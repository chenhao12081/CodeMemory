## 大模型的发展

1. 奠基期 (2013 - 2017)：向量化时代的开启。AI 开始学会把词变成数字， Google 提出 **Word2Vec**，让电脑第一次发现“国王 - 男人 + 女人 = 女王”。2017年transformer的提出，发明了自注意力机制，使模型能够同时处理整句话，解决了模型记不住长句子的问题。
2. 2020年-2022年，模型参数大爆发与涌现，模型参数规模到达1750亿级别，随着模型规模的增大神奇的事情发生了，它展现了训练数据中没有的能力，比如简单的逻辑推理和代码能力
3. 2022年-2024年，全民时代，对话即服务。chatGpt将LLM包装成对话界面，引爆全球。**GPT-4 & Claude 3 (2023-2024)**：模型进入**多模态**（能看图、听声音）和**强逻辑**时代
4. 未来与发展，从聊天到办事。LLM 正在从单纯的对话工具转向**智能体 (Agent)**

### 概念

**从翻译问题说起**

比如一个句子：货拉拉拉不拉拉布拉多。这句话人通过大脑能够翻译成人理解的意思，可是电脑是怎么来理解这句话呢

**token和向量**

为了让计算机可以理解，我们可以把句子分隔成一个个token（词元），然后对他们进行编码比如unicode编码

`货拉拉  拉不拉 拉布拉多`

但是只是单纯的编码计算机还是读不懂每个词元的信息。

所以我们对他进行向量化(`embedding`)，将词元向量化赋予它一个坐标，坐标轴是每个维度，比如运输工具，宠物，物流平台，网约车等等，随着维度的增大，词元的信息越准确。同时词元也是多义词，受在句子的位置影响，前后的词元会把其拉向正确的语意意思，因此要在坐标中加入位置信息。

同时向量化后可以加减，比如国王-男人+女人=女王

**QKV是什么**

在向量化后我们可以考虑进行翻译了，首先一个词元会有很多的含义。

上面整套流程就是注意力机制：

首先会Q.K得到应该重点关注哪个词元，scale会防止维度过大导致关注度值过高带来softmax的权重梯度消失，softmax得到一组权重，再乘以v可以得到这一组词元的权重比例。

多头注意力：

但只算一次注意力是不够的，词与词之间的关系是多样的，但是单一角度很难捕捉全面，所以模型会并行做多次注意力计算，每一次关注不同的侧重点，这些并行的注意力会被拼接到一起形成多头注意力机制。

多头注意力得到了一组向量：会进行Add，将注意力输出向量与原有token相加保障原有的词元语意不被覆盖，然后进行归一化（Norm）将向量值变为0-1之间。

**前馈网络**

虽然我们经过残差相加和归一化后得到了新的输出，但是输入和输出的变化都是线性的，没办法捕获复杂的语意关联。

为了让模型具备更强的语意表达能力，拟合自然语言里非线性的语意关系，模型会让向量通过FNN（前馈网络），里边有ReLU函数可以把线性的路径掰弯变成非线性的曲线。然后再进行一次Add和Norm

**翻译原理**

接下来就是把计算机的整体语意理解翻译成英文，生成英文时我们会放一个固定标识`<BOS>`它表示英文从这里开始翻译。接着模型会从编码器的输出的中文理解预测最合理的第一个英文单词，然后会把BOS和第一个英文单词一起输入，再预测下一个最合理的单词![image-20260307110734056](/Users/chenhao/code/study_md/${image}/image-20260307110734056.png)，以此类推结合上一个词，预测下一个最合理的词。为了保障预测的单词符合整体的语意，要再进行注意力机制，生成第n个词，只要关注前n-1个词即可，这被称为带掩码的多头注意力机制。

![image-20260307110829455](/Users/chenhao/code/study_md/${image}/image-20260307110829455.png)

为了解决当前的词应该对应中文的哪个部分，会用注意力机制，query是当前的英文词，key,value是中文词块数据库，这被称为多头交叉注意力。

同时两个注意力也会经过Add和Norm并通过FFN，这组成了一个解码层，多个解码层组成一个解码器。每一层都在上一层的基础上进一步加工解释。最终将输出的向量通过词表转化成可读的文字也就是英文输出。

### 提示工程简介

#### 模型设置

使用提示词时，您通常会通过 API 或直接与大语言模型进行交互。你可以通过**配置一些参数**以获得不同的提示结果。调整这些设置对于提高响应的可靠性非常重要，你可能需要进行一些实验才能找出适合您的用例的正确设置。以下是使用不同LLM提供程序时会遇到的常见设置：

`Temperature`和`Top_p`用来空值模型生成的随机性，值越小确定程度越高适合确定程度较高的任务比如QA，值越大，随机性越大，适用于诸如诗歌生成等任务。一般建议是改变 Temperature 和 Top P 其中一个参数就行，不用两个都调整。

`Max Length`控制生成的token数

`Stop Sequences`控制大模型响应长度和结构的另一种方法

`Frequency Penalty`对重复出现的token进行惩罚，出现的越多惩罚的越大

`Presence Penalty`对重复出现token惩罚，与出现次数无关。

#### 链式提示 prompt chaining

普通的prompt让大模型完成一个普通的任务，而prompt chaining则是完成一项工程

什么是 Prompt Chaining？

**Prompt Chaining** 是指将一个复杂的任务拆解为多个**连续的、小的子任务**。上一个 Prompt 的输出，会作为下一个 Prompt 的输入（或者输入的一部分）。

- **直观比喻**：就像工厂的**流水线**。第一站负责切割木材，第二站负责打磨，第三站负责组装。你不会要求一个工位直接把原木变成沙发。
- **核心逻辑**：LLM 在处理单一简短逻辑时准确率极高，但在处理长篇大论或多步骤逻辑时容易“断片”或产生幻觉。通过 Chaining，你把逻辑压力分摊到了每一个环节。

一个实战案例：写一篇高质量深度技术文章

如果你直接问：“写一篇关于量子计算的文章”，结果通常很平庸。 使用 **Prompt Chaining**，流程如下：

- **Prompt 1 (大纲生成)**：

  > “请为关于量子计算的深度科普文章列出一个逻辑严密的大纲。”

- **Prompt 2 (资料搜集/验证)**：

  > （输入 Prompt 1 的结果） “针对这个大纲的每一个小节，请列出需要讲解的核心科学概念和最新的实验数据。”

- **Prompt 3 (内容撰写)**：

  > （输入 Prompt 2 的结果） “请根据以上大纲和核心概念，用生动幽默的语言撰写文章的第一章：量子叠加态。”

- **Prompt 4 (校对与润色)**：

  > （输入 Prompt 3 的生成内容） “请检查以上段落是否存在事实性错误，并优化其在手机端阅读的排版。”

进阶：从手工链到自动化链

**LangChain / Flowise**：这些工具可以帮你把这些 Prompt 用线连起来，自动运行。

**Agentic Workflow**：这是 2026 年最火的概念。模型不仅是在跑链条，它还会根据上一步的结果，**自动决定**下一步该跑哪一个 Prompt。

#### 思维树

思维树是一个解决复杂问题的框架。他把大问题拆解成几个小阶段，然后每个阶段提出几种方案，再通过大模型审核，根据评分结果决定走下去还是换个分叉（广度优先搜索算法）

#### 检索增强生成（RAG）

幻觉：大模型在一本正经的胡说八道。

大语言模型可以解决常见的问题，但是当面对更加专业的内容时，就需要我们去构建一个系统，去访问外部的知识源，来获得更加专业的答案，而且可以解决大模型的幻觉。并且大模型的参数都是静态的，我们通过RAG让语言模型不用重新训练就能够获取最新的信息，基于检索生成产生可靠的输出。

 RAG 是一种可行的方案，能在知识密集型任务中增强语言模型的输出。

#### ART 自动推理并使用工具 & ReACT框架

大模型有两个问题，一个是无法获取最新的信息比如天气、股价，不擅长复杂计算，容易算错数字。因此我们可以借助工具来解决问题：

+ 我们提供一套工具（比如天气接口，工具箱，搜索API）给模型
+ 模型当意识到这个问题自己直接回答不了时，它会输出一段代码（通常是json格式），便去请求调用工具，系统运行工具将结果返回给模型，模型再基于这个结果生成答案。

自动推理：ReAct框架

这是目前最经典的自动推理框架。模型不再是直接给出答案，而是遵循**“思考 -> 行动 -> 观察”**的循环：

- **Thought (思考)**：模型分析当前问题，决定下一步该做什么。
- **Action (行动)**：模型选择并调用一个工具。
- **Observation (观察)**：模型读取工具返回的结果。
- **Final Answer (最终答案)**：如果信息足够，则输出结果；如果不够，回到第一步继续思考。

**举个例子：**

> **用户问**：“姚明的妻子现在多少岁？”
>
> 1. **思考**：我需要先知道姚明的妻子是谁，然后查她的出生日期，最后计算年龄。
> 2. **行动**：调用搜索工具查询“姚明的妻子”。
> 3. **观察**：结果显示是“叶莉”。
> 4. **思考**：现在我需要查叶莉的出生日期。
> 5. **行动**：调用搜索工具查询“叶莉 出生日期”。
> 6. **观察**：结果显示“1981年11月20日”。
> 7. **思考**：现在是 2026 年，计算 2026 - 1981。
> 8. **最终答案**：叶莉现在 44 岁。

#### 程序辅助语言模型（PAL）

PAL解决大模型的问题；逻辑推理能力很强但是算数计算很烂。而计算机又在计算方面特别擅长。因此PAL思路是：大模型不直接计算，而是写程序，让计算机来执行和计算。

#### reflexion 自我反思

PAL相当于给大模型上了一个计算器，而自我反思相当于给大模型上了一个监考老师

**传统模式**：输入 ->模型生成->结束。

**反思模式**：输入 -> 模型生成初稿 ->**模型自我检查（找错）** ->**模型根据错误修改** ->输出终稿。

## LLM入门基础

### 概念：

prompt：与大语言模型交互的自然语言文本被称为prompt

上下文窗口；能容纳的prompt的大小或者memory，被称为上下文窗口，通常有几千字大小，与模型有关

模型的输出被称为完成（completion），用模型生成文本的行为被称为推理

一个流行的领域是将大模型与外部数据源链接或者调用外部API来增强大模型的能力

模型的参数越大它能越好的帮你完成推理任务，但是一些较小的模型可以被很好的调优，从而在一些特定领域上表现的优秀。通常来说一个模型多少B（十亿）就是指它的参数多少



### 支撑大模型的架构

早期的语言模型使用一种叫做循环神经网络或者RNN的架构。RNN需要大量的内存和计算来预测下个内容，RNN在预测文本时，只能看到前一个词，这种预测效果不好，当增大RNN能看到的次数时，就需要增大其使用的资源。

transformer架构会了解到每个词之间的相关性以及其上下文。

多头注意力会并行地进行，同时每个头会关注不同的方面，比如，一个头看到句子中人的实体之间的关系，另一个头可能关注句子的活动，另一个头可能会关注词的其他属性，比如词是否是押韵。多头的数量会因模型而不同，一般是12到100个。我们不能提前决定注意力头学习语言的哪个方面，每个头的权重都是随机初始化的，给定足够的训练数据和时间，每个头都将学习语言的不同方面。

大模型是怎么输出的：通过编码器的序列已经包含了大模型对输入的结构和含义的深层表示，然后将这个输出插入到解码器中，根据最后一个token，去预测下一个token，输出的token在反馈到输入中，以触发爱一个Token的生成，直到模型预测出一个序列结束的token。

有多种方式可以使用soft Max层的输出来预测下一个token，这些方式会影响我们生成文本的创造性。

总的来说大模型分为编码器和解码器，编码器将输入序列编码为输入的结构和含义的深层表示。解码器从输入 Token触发器开始工作，使用编码器的上下文理解生成新的Token。它以循环的方式进行，直到达到某个停止条件。





我们也可以将组件分开作为变体的架构，仅编码器也可以作为翻译模型工作。包括仅解码器模型，包括GPT等。

### 单一任务进行微调

如果我们的模型只进行单一任务，这种情况下我们可以对预训练模型进行微调，只提高你感兴趣的任务的性能。例如对特定任务的示例数据集摘要，有趣的是，即使例子相对较少，也可以取得较好的结果，通常来说只需要500-1000个例子便能取得成功。

但是对单一任务进行微调可能导致一种叫做灾难性遗忘（Catastrophic Forgetting）的现象。灾难性遗忘发生是因为全面微调过程中会改变原是LLM的权重，它会提升在单一任务上的性能，但是会降低其他任务的性能。

如何避免灾难性遗忘：

1. 首先确定灾难性遗忘是否真的影响到你的使用场景了
2. 可以在多个任务上进行微调，良好的多任务微调可能需要50-100000个例子来跨多个任务
3. 选择参数有效的微调（PEFT，Parameter Efficient Fine-tuning）而不是全面微调，PEFT这种技术只会保留原始LLM权重，并且只训练少量特定任务的适配器层和参数。

### 多任务指令微调

多任务是单任务的延展，其中数据集是由多个任务的示例输入和输出组成。这里数据集包含了让模型执行各种任务的示例。我们在这个混合数据集上训练模型，以便同时提高模型在所有任务上的性能，从而避免灾难性遗忘的问题。在许多的训练周期中，通过计算各个示例的损失来更新模型的权重，从而得到一个经过指令调整的模型，这个模型可以同时在许多不同的任务上表现良好。

多任务微调的一个缺点是它需要大量的数据，可能在训练集中有50-100000个示例。

## node 流式操作

为什么需要流式操作：

传统的文件操作，比如`fs.readFile`，读取文件会先准备一块足够大的地方，一次性读入文件，当文件体积小的时候尚可，但对于单文件操作来说，就需要流式操作。

流式操作不是一次行读入所有数据，而是想传送带一样，一块一块地传输。它可以分为可读流(ReadableStream)与写入流(WriteableStrea)，也可以看作数据的生产者与消费者。

### 可读流

可读流就像一个中转站，它一边读取文件，一边将它运输到目的地。它有两种模式：

1. 流动模式：数据自动从底层系统读取，并通过事件尽快提供给应用程序，像是打开水龙头，水一下子流出来
2. 暂停模式：消费者必须显示调用`strea.read()`方法从流中读取数据，像是抽水泵，你按一下它出一下水

常见的可读流有

1. `fs.createReadStream()`：读取本地文件
2. `http.IncomingMessage`：服务器收到的`req`对象
3. `process.stdin`：标准的输入
4. `zlib`压缩流

可读流的操作：

事件监听操作

```js
const fs = require('fs');

const readStream = fs.createReadStream('./圣墟.txt', { encoding: 'utf-8' });

readStream.on('data', (chunk) => {
    console.log('读取到了数据长度为', chunk.length, '内容');
});

readStream.on('end', () => {
    console.log('读取完成');
});

readStream.on('error', (err) => {
    console.log('读取错误', err);
});
```

我们读取小说这个文件，从输出可以看出，是分块读取的

![image-20260315154111020](/Users/chenhao/code/study_md/${image}/image-20260315154111020.png)

可读流有个关键参数`HighWaterWork`，决定了流在停止读取底层资源之前，能在内部缓冲区里缓存多少数据，这设计到了背压机制（nodejs为了防止消费者消费慢，生成者生产快，而导致内存溢出的保护机制），通常默认是64KB。

### 可写流

可写流是数据的目的地，它接受来自可读流的数据块，然后将其写入底层设备如硬盘、网络 Socket、控制台等）。

常见可写流有

1. `fs.createWriteStream()`文件写入
2. `http.ServerResponse`web开发中的`res`对象，把数据发回给浏览器
3. `process.stdout`标准输出
4. `zlib.createGzip()`压缩流
5. `crypto.createHash()`加密流

`fs.createWriteStream`的操作举例来说

```js
const fs = require('fs');

const readStream = fs.createReadStream('./圣墟.txt', { encoding: 'utf-8' });
const writeStream = fs.createWriteStream('./copy.txt', { encoding: 'utf-8' });

readStream.on('data', (chunk) => {
    // console.log('读取到了数据长度为', chunk.length, '内容');
    writeStream.write(chunk);
});

writeStream.on('finish', () => {
    console.log('所有内容写入到copy.txt文件');
});
```

可写流有两个关键状态:

**`write()` 的返回值**：

- 如果返回 `true`：说明缓冲区还没满，你可以继续疯狂写入。
- 如果返回 `false`：说明缓冲区满了（超过了 `highWaterMark`），你应该停下来，等待 **`drain`** 事件。

**`drain` 事件**：

- 当缓冲区的数据被成功处理掉、可以重新接收新数据时，会触发这个事件。这是处理大批量数据而不撑爆内存的关键

### pipe & pipeline

pipe是node中非常重要的一个api，它像一个水管连接可读流和可写流，并且能自动处理背压，防止数据撑爆内存。

pipe连接可读流与可写流，在使用时只需要可读流调用pipe方法，传入一个可写流即可

例如：

```js
const fs = require('fs');

const readStream = fs.createReadStream('./圣墟.txt', { encoding: 'utf-8' });

const writeStream = fs.createWriteStream('./copy.txt', { encoding: 'utf-8' });

readStream.pipe(writeStream);
```

而且pipe返回的是流，你可以在中间加个过滤器，比如

读文件->Gzip压缩->传输给浏览器

```js
const zlib = require('zlib');

// ... 在 server 回调中
res.writeHead(200, { 'Content-Encoding': 'gzip' });

fs.createReadStream('index.html')
  .pipe(zlib.createGzip()) // 中间加个压缩层
  .pipe(res);              // 最后给响应
```

pipe的优势在于

+ **`.pipe()`** 是处理 I/O 的最高效方式，因为它只占用极小的内存（Buffer 块）。

+ **它连接了生产者和消费者**。

+ **在 Web 场景中**，它是实现文件下载、视频串流、日志读取的最佳实践。

对于pipe也有缺点，如果中间某个流错了，它不会自动销毁其他流，容易导致内存泄漏。Node.js 官方现在推荐使用 `stream.pipeline`，它能更安全地处理错误，用法如下：

```js
const { pipeline } = require('stream');

pipeline(
    fs.createReadStream('large-file.txt'),
    zlib.createGzip(),
    res,
    (err) => {
        if (err) {
            console.error('传输过程中出错:', err);
            res.end();
        } else {
            console.log('传输圆满完成');
        }
    }
);
```

pipe应用实例，将文件流导向HTTP响应：

```js
const http = require('http');
const fs = require('fs');
const path = require('path');

const server = http.createServer((req, res) => {
    const filePath = path.join(__dirname, 'movie.mp4'); // 假设是一个很大的视频文件
    
    // 1. 获取文件状态，以便设置正确的响应头（可选但专业）
    fs.stat(filePath, (err, stats) => {
        if (err) {
            res.writeHead(404);
            return res.end('File not found');
        }

        // 2. 设置 Header
        res.writeHead(200, {
            'Content-Type': 'video/mp4',
            'Content-Length': stats.size
        });

        // 3. 核心：创建可读流并 pipe 到 res (可写流)
        const readStream = fs.createReadStream(filePath);
        
        // 这一行代码完成了所有工作：读取、传输、错误处理关联
        readStream.pipe(res);

        // 4. 监听结束（可选）
        readStream.on('end', () => {
            console.log('文件传输完成');
        });
    });
});

server.listen(3000, () => console.log('Server running at :3000'));
```

## SSE

SSE(Server-send Events)是一种让服务器向浏览器单向推送实时数据的技术。

SSE可以建立一个持久链接，服务器可以把数据一波一波地发给浏览器。

为什么要SSE

| **技术**             | **交互模式**                         | **优点**                                               | **缺点**                                       | **适用场景**                                   |
| -------------------- | ------------------------------------ | ------------------------------------------------------ | ---------------------------------------------- | ---------------------------------------------- |
| **短轮询 (Polling)** | 浏览器每隔 1 秒问一次：“好了吗？”    | 简单，兼容性极好。                                     | 浪费流量和性能，延迟高。                       | 扫码登录、简单的状态检查。                     |
| **WebSocket**        | 全双工（双向自由对话）。             | 延迟最低，支持双向通信。                               | 协议复杂，由于是长连接，对服务器资源消耗较大。 | 实时聊天、多人协作、网游。                     |
| **SSE**              | **单向推送（服务器写，浏览器读）。** | **极轻量**，基于 HTTP 协议，自带重连机制，开发最简单。 | 只能由服务器发往浏览器。                       | **AI 回答流（ChatGPT）**、实时股价、日志监控。 |

为什么现在的 AI 产品（如 ChatGPT）都用 SSE？

如果你使用普通的 JSON 请求获取 AI 的回复：

1. 你提出问题。
2. 你盯着屏幕等 30 秒，期间一片空白（AI 在后台生成全文）。
3. 30 秒后，一整段文字突然蹦出来。 **这种用户体验非常糟糕。**

**使用 SSE 之后：**

1. AI 生成一个词，服务器就推一个词。
2. 前端实时把收到的词显示出来。
3. 用户看到的就像是 AI 在现场“打字”一样，**体感延迟几乎为零**。

4. SSE 的核心特点

5. **基于 HTTP 协议**：它不需要像 WebSocket 那样升级协议，普通的 Web 服务器（Nginx, Apache）只要简单配置就能支持。
6. **断线重连**：浏览器会自动尝试重新连接，无需你写复杂的重连逻辑。
7. **单向性**：非常适合那种“我问一个问题，你给我一段很长输出”或者“我订阅一个结果，你持续告诉我进度”的场景。
8. **轻量级**：它传输的是纯文本，头部开销非常小。

SSE 协议对数据格式有严格要求，必须是文本流，且以 `data: ` 开头，以两个换行符 `\n\n` 结尾：

```
data: {"word": "Hello"}

data: {"word": "world"}

data: [DONE]
```

后端实现 (Node.js 原生)

关键点在于设置正确的 **HTTP 响应头**，并使用 `res.write` 而不是 `res.end`。

JavaScript

```
const http = require('http');

http.createServer((req, res) => {
    if (req.url === '/events') {
        // 1. 设置 SSE 核心响应头
        res.writeHead(200, {
            'Content-Type': 'text/event-stream', // 必须是这个类型
            'Cache-Control': 'no-cache',         // 禁止浏览器缓存
            'Connection': 'keep-alive',          // 保持长连接
            'Access-Control-Allow-Origin': '*',  // 允许跨域（本地调试常用）
        });

        // 模拟 AI 逐步生成回复的数据流
        const message = "你好！我是 Gemini，很高兴能为你演示 SSE 技术。";
        const words = message.split("");
        let index = 0;

        // 2. 定时推送数据块
        const intervalId = setInterval(() => {
            if (index < words.length) {
                // SSE 格式：data: <内容>\n\n
                res.write(`data: ${JSON.stringify({ char: words[index] })}\n\n`);
                index++;
            } else {
                // 推送一个结束标志
                res.write('data: [DONE]\n\n');
                clearInterval(intervalId);
                res.end(); // 结束响应
            }
        }, 100); // 每 100 毫秒推一个字

        // 3. 客户端主动关闭连接时的处理
        req.on('close', () => {
            clearInterval(intervalId);
            console.log('客户端已断开连接');
        });

    } else {
        res.writeHead(404);
        res.end();
    }
}).listen(3000, () => {
    console.log('SSE Server 运行在 http://localhost:3000/events');
});
```

2. 前端实现 (JavaScript)

前端使用浏览器自带的 `EventSource` 接口，它会非常优雅地处理连接和接收。

HTML

```
<!DOCTYPE html>
<html>
<body>
    <h1>AI 回答演示：</h1>
    <div id="content" style="border: 1px solid #ccc; padding: 10px; min-height: 50px;"></div>

    <script>
        const contentDiv = document.getElementById('content');
        
        // 建立连接
        const eventSource = new EventSource('http://localhost:3000/events');

        // 监听消息事件
        eventSource.onmessage = (event) => {
            if (event.data === '[DONE]') {
                console.log('传输结束');
                eventSource.close(); // 主动关闭连接
                return;
            }

            const data = JSON.parse(event.data);
            contentDiv.innerHTML += data.char; // 实时显示收到的字符
        };

        // 错误处理
        eventSource.onerror = (err) => {
            console.error('SSE 异常:', err);
            eventSource.close();
        };
    </script>
</body>
</html>
```

3. SSE 消息格式详解

SSE 的协议非常简单，但格式要求极其严格。每条消息由一个或多个 `field: value` 组成，以两个换行符 `\n\n` 结束。

| **字段名**  | **说明**                                               | **示例**                       |
| ----------- | ------------------------------------------------------ | ------------------------------ |
| **`data`**  | 消息的正文。如果数据太长，可以分成多行 data。          | `data: {"id": 1}\n\n`          |
| **`event`** | 自定义事件名称。前端可以用 `addEventListener` 监听。   | `event: update\ndata: 123\n\n` |
| **`id`**    | 消息 ID。如果掉线，浏览器会带上 `Last-Event-ID` 请求。 | `id: 1001\ndata: msg\n\n`      |
| **`retry`** | 告诉浏览器断线后重连的时间间隔（毫秒）。               | `retry: 5000\n\n`              |

4. 为什么要在生产环境小心 Nginx？

如果你在 Nginx 后面运行 Node.js SSE 服务，你会发现“打字机”效果消失了，数据会攒一大波才一起出来。

**原因**：Nginx 默认开启了**响应缓冲（Buffering）**，它想攒够一定数量的数据再发给用户以节省开销。

**解决办法**：在 Nginx 配置中针对该路径关闭缓存：

Nginx

```
location /events {
    proxy_buffering off;
    proxy_cache off;
    chunked_transfer_encoding on;
}
```

总结

实现 SSE 只需要三步：

1. 后端设置 `text/event-stream`。
2. 后端按照 `data: ...\n\n` 格式不断 `res.write`。
3. 前端用 `new EventSource()` 接收。

### streamText

### 格式化返回 & generateObject

`streamText`是在和你聊天，`generateObject`是在帮你做事

`generateObject`是`vercel AI SDK`的一个核心函数，他目标是消除大模型输出的不确定行。

`generateObject`强制模型返回一个结构化对象(JSON)，它会在底层通过 Prompt 提示、模型约束（如 OpenAI 的 JSON Mode 或 Function Calling）来确保模型吐出的每一比特数据都符合你预定义的格式。AI SDK 会把 Zod Schema 转换成模型能理解的指令（如 JSON Schema），告诉 AI：“你必须按这个格式写，不准废话”。

如果不这样的话，ai 可能会随机输出，比如：模型可能心情好回你 `{ "price": 100 }`，心情不好回你 `{ "cost": "100元" }`，后端逻辑会直接崩

#### zod Shema

Zod是一个TypeScript 优先的类型定义和验证库。你用代码描述数据长什么，比如（`name`是字符串，`age`是必须大于0的数）。当数据进来的时候，Zod会检查它是否符合要求，如果不符合直接报错。

 #### api

Vercel在6版本增强了generateText使它可以返回对应结构的回答，相比较于`generateObject`强制模型输出JSON，`generateText`允许模型先输出一段文字分析，最后输出一个JSON结构数据。而现在模型在生成JSON结构前会进行思维链推理，而`generateObject`有时会强制模型生成JSON，而跳过了思考步骤，从而降低复杂任务的准确性。

而且使用`generateText`可以获得统一的API体验，在对话体验过程中加入`schema`即可。并且有时侯我们并不单单需要一个JSON结果，而是想要对话过程中决定什么时候去触发一个结构话动作，`generateText的tool也是基于schema`，相较于`generateObject`更灵活。

`generateText`或`streamText`规定结构话数据，只要给output传参即可，文档：https://ai-sdk.dev/docs/reference/ai-sdk-core/generate-text#output

例如：

```js
import express from 'express';
import { ollama } from 'ollama-ai-provider-v2';
import { generateText, Output, convertToModelMessages } from 'ai';
import { z } from 'zod';

const app = express();

app.use(express.json());
app.post('/chat', async (req, res) => {
    console.log(req.body);
    const { prompt } = req.body;

    const recipeSchema = z.object({
        recipe: z.object({
            name: z.string(),
            ingredients: z.array(z.string()),
            calories: z.number(),
        }),
    });

    const { output } = await generateText({
        model: ollama('qwen2.5'),
        prompt,
        output: Output.object({
            schema: recipeSchema,
        }),
    });
    console.log('output: ', output);
    res.setHeader(
        'Access-Control-Allow-Origin', '*',
    );
    res.json(output);
});

app.listen(3000, () => {
  console.log('Server is running on port 3000');
});
```

# RAG

RAG: 

+ R(retrieval-检索)，用户提问时先去数据库搜索与问题最相关的切片
+ A(Augmented-增强)，系统把搜索出来的片段和用户的原始问题拼接到一起，形成一端更丰富、增强版的提示词
+ G(generation-生成)，把增强后的提示词发给大模型，让大模型生成最终的自然语言回答

RAG技术是为了解决

1. AI不懂你的私有数据（比如个人笔记、公司内部文档）
2. AI的知识库没有实时更新（比如他不知道昨天的新闻）
3. 大模型的上下文窗口有限（不能每次把几百万文字的文档喂给他，不仅贵，ai还记不住）

通俗理解RAG就是给“文科状元”一次开卷考试

如果想象大模型是极其聪明的文科状元，但你问他你公司请假流程是什么，他并不知道，而使用RAG后，相当于在问他之前，你的检索系统，先去公司档案库里，翻出员工手册那一页，并把这一页递给文科状元，说“基于这一页回答这个问题”。

RAG的核心是，切片->向量化->检索->生成。

## 向量化

向量化用的模型和我们经常使用的模型还不是一个，AI模型分为两类：

1. 生成模型，比如，千问，DeepSeek，擅长说话，写代码，聊天。
2. 向量模型，专门负责切片变数字的Embedding模型，比如`bge-m3`(智源研究院)，`text-embedding-3-small`(openAI)。

不同模型的跑出来的维度是不相同，是不能用做匹配的，存与取必须是同一模型跑出来的向量，否则什么也得不到。

RAG里的向量化是将整个切片压缩成一个向量，这个向量代表了这段话的中心思想，我们需要把这个向量存入向量数据库中，搜索的时候我们要去拿用户的中心思想去匹配文档切片的中心思想。

## 切片

优秀的切片需要额外关注两个技巧：

1. 保持重叠：为了防止把一句完整的话或一个完整的概念从中间一刀切，导致语意丢失，切分时会让相邻阶段保留一定的重叠部分，像盖瓦片一样，保持上下文的完整。
2. 尊重语义边界，优秀的切片不会机械地数到500字就硬生生砍掉，而是按照自然语言的逻辑，顺着标点符号或文档结构进行切分。

# Agent

## 什么是agent

智能体在于系统本身，一个系统可以自主才能称为智能体。智能体的自主性可以有高有低。



智能体是？一个推理动手记忆能力于一身的应用，他需要以下几个要素：大模型+工具+记忆。智能体不是线形地工作，他会拆解任务，应用多步操作来完成复杂任务。



agent 的核心是函数调用：很多人觉得大模型神了，能去自己去执行代码，但真相是大模型自己不能执行任务代码，它只是输出了一段JSON。真实的开发流程是我们告诉大模型有哪些函数，当大模型对于用户问题没法直接回答时，会直接输出一段特殊JSON，例如`{"action": "call_function", "name": "getWeather", "arguments": {"city": "Osaka"}}`，然后后端代码会拦截到这个JSON，发现大模型想要调用工具，于是代码就去真真切切执行了函数，然后将执行结果传回给大模型，大模型最终输出。



所有agent框架在底层做的事：解析大模型的JSON -> 执行本地代码 ->把结果喂回给大模型

### Agentic workflow

用写一篇文章举例，Agentic workflow会先询问是否需要网上调研，在读取网上文章后会问先写一篇草稿，再针对草稿进行针对性修改，这样重复动作。

agentic workflow指的是LM应用执行多步操作来完成任务。

对于agent来说重要的是学会如何处理复杂任务，并将其拆解为更小的步骤，让代理形流程逐步执行，最终获得想要的工作产出。以及如何构建组件来高效执行每个步骤。

## 智能体评估

通常我们在制定完智能体流程后，我们还需要不断迭代和优化流程，如何评估智能体就非常重要了。

对于一些问题来说，可能会有很多意外的情况出现，我们很难提前预知到这些问题。因此推荐直接查看输出结果，手动找出希望系统能够做的更好的地方。比如，一个购物客服的智能体，查看发现频繁出现竞争对手的名字，这个在之前很难预料到，而我们不希望提及竞争对手，因此最佳实践是先构建系统，然后检查它哪些地方不令人满意，然后找到对应方法优化这块内容。



目前来说智能体的评估有：

+ 对于客观指标，我们可以编写代码统计出现频率，以此来改进
+ 可以使用大模型对智能体的输出在评审
+ 端到端评估，衡量整个智能体的输出质量
+ 组件级评估，评估智能体每一步的输出质量

### 智能体设计模式

+ Reflection
+ Tool use
+ Planning
+ Multi-agent collaboration



#### Reflection

反思，让llm去检查自己的输出或者引入一些外部来源，比如运行代码，看看是否有错误信息，并用这些反馈再次迭代，生成更优的输出版本。

#### 通过反思提高任务输出质量

我们可以通过llm先写出一个初稿，然后再通过llm进行反思和优化，得到第二版。

有时候外部信息对于反思和改进十分重要，比如代码执行的错误信息，有助于llm反思并改进。

#### 反思流程的评估方法

对于一些问题，比如让llm写查询数据的SQL语句，我们可以建一个数据集，分别让初版的SQL和经过反思改进后的模型去跑，查看正确率和改进多少。

我们也可以通过大模型去评估反思流程的改进效果，比如我们可以指定一些指标，让大模型去评判。

#### 使用外部反馈

使用外部反馈效果超过仅依靠于语言模型自身反馈的反思。

外部反馈可以是生成代码的运行结果，或者外部搜索的权威信息，或者一个工具等等来引入外部信息，帮助大模型反思。

### 评估

有时候我们在开发智能体的时候很难预料到哪个部分表现好，哪个部分表现不好，我们可以先把系统搭建出来，再进行评估，针对表现不好的部分进行优化。

#### 端到端评估

评估的方式也是很灵活的，比如我们针对一项提取发票日期的智能体，我们可以建立一个小型评估数据集，标注正确的日期，然后来评估智能体提取日期的正确率。比如针对一个要求提供十字以内标题的标题摘要智能体，我们可以准备问题，写代码统计最后智能体输出的字数，来评估。比如针对一个写作的智能体，我们可以提供一个小型评估数据集，用写作后文章的核心关键点做指标进行评估。总的来说，对于评估，我们只需要关心我们智能体的核心功能，并以此来设计指标，既可以是客观的指标，也可以让大模型来进行评估，这种方式通常被称为端到端的评估。

评估也是可以我们建立一个初步的评估，然后慢慢优化，或者更新评估方式。

#### 误差分析及确定后续步骤优先级

有两个概念：

trace: 整个智能体的工作周期

span：一个节点完成工程的过程



我们可以查看中间环节的输出，已更好了解各环节的表现优劣，可以统计各环节不满意的地方，然后统一汇总看是哪个环节最不满意然后优化。

#### 组件级评估

我们如果确定了某一组件需要优化，如果使用端到端评估，虽然可以获得较好的优化效果，但是需要整个智能体流程跑一遍，代价较大，而且替换某一组件进行测试可能给其他组件引入噪声，影响优化的观察。

现今的大模型都对工具调用做了优化，在最初未优化去，原生的调用方式，想要工具调用需呀如下方式，在system prompt中给他提示：

工具调用的方式有以下几种

1. 定义静态数据，调用大模型的时候直接全传给它，但是上下文窗口有限，传给大模型定义的工具有限
2. 定义在数据库中，我门去查
3. 让大模型自己写代码解决问题，例如，但使用eval执行代码会具有风险，最佳实践是在沙盒环境中执行

在开发AI Agent的时，工具调用已经形成了一套相对标准化的的规范，主要是由openai、目前Gemini、Anthropic以及各类开元模型也基本兼容或采用类似的结构。



整个工具调用的生命周期主要包括三个核心数据结构？工具定义的`Json Schema`、大模型决定调用工具的返回结果、将工具执行结果交还给大模型的格式。



### 工具定义的Json Schema

这个数据结构向大模型描述工具是什么，有什么用，需要哪些参数，这个需要我们在第一次调用同用户需求携带的信息。

以天气调用的结果举例，格式如下：

```json
{
  "type": "function",
  "function": {
    "name": "get_current_weather",
    "description": "获取指定地点的当前天气情况",
    "parameters": {
      "type": "object",
      "properties": {
        "location": {
          "type": "string",
          "description": "城市或地区名称，例如：北京市、上海市"
        },
        "unit": {
          "type": "string",
          "enum": ["celsius", "fahrenheit"],
          "description": "温度单位，默认为 celsius（摄氏度）"
        }
      },
      "required": ["location"]
    }
  }
}
```

**核心字段解析：**

- **`name`**：函数名，必须是纯英文字母/数字/下划线。
- **`description`**：**极其重要**！大模型完全依赖这段自然语言描述来决定是否需要调用该工具。
- **`parameters`**：标准的 JSON Schema 格式，用于约束大模型输出的参数类型（`type`）、枚举值（`enum`）以及必填项（`required`）。

### 大模型决定工具调用的返回格式（触发工具调用）

当大模型遇到没法解答的问题时，触发工具调用，它会停止生成普通文本，并返回一个`tool_calls`的特殊响应

```js
{
  "role": "assistant",
  "content": null, 
  "tool_calls": [
    {
      "id": "call_abc123def456", 
      "type": "function",
      "function": {
        "name": "get_current_weather",
        "arguments": "{\"location\": \"北京市\", \"unit\": \"celsius\"}"
      }
    }
  ]
}
```

**核心字段解析：**

- **`content`**：通常为空（null），因为模型当前的任务是调用工具而不是直接回答。
- **`tool_calls`**：一个数组（支持一次性并发调用多个工具）。
- **`id`**：本次工具调用的唯一标识符（非常重要，后续返回结果时需要对齐这个 ID）。
- **`arguments`**：大模型根据用户的自然语言输入，自动提取并生成的 JSON **字符串**（注意：这里通常是一个字符串化后的 JSON，你在代码中需要先 `JSON.parse` 才能使用）。

### 工具调用的结果（返回给大模型）

本地代码（Agent 框架）拿到大模型给的 `arguments` 后，去调用真实的天气 API。拿到真实数据后，你需要按照特定的 `role: "tool"` 格式将结果拼接到历史对话中，并再次请求大模型。

```json
{
  "role": "tool",
  "tool_call_id": "call_abc123def456", 
  "name": "get_current_weather",
  "content": "{\"temperature\": 22, \"condition\": \"晴朗\", \"wind\": \"东北风3级\"}"
}
```

**核心字段解析：**

- **`role`**：必须是 `"tool"`（有些老版本的 API 中可能是 `"function"`）。
- **`tool_call_id`**：必须与大模型刚才返回的那个 `id` 完全一致，这样大模型才知道这是哪个工具的执行结果。
- **`content`**：你实际调用的 API 返回的结果，通常转化为 JSON 字符串传给模型。

### openai deepseek天气查询代码实例

手动实现工具调用是深入理解大语言模型底层交互机制的最佳方式。剥离高层 SDK 的封装，Agent 的核心本质其实就是一个**多轮对话的“检查与执行”循环**。

核心四个步骤：

1. **定义工具 (Tool Definition)：** 用 JSON Schema 告诉大模型你有哪些函数、需要什么参数。
2. **首次调用 (First LLM Call)：** 将用户的提问和工具列表一起发给大模型。
3. **解析与执行 (Execution)：** 判断大模型的返回结果。如果它认为需要查天气，它会返回一个带参数的指令（而不是直接回复文本）。你在后端拦截这个指令，执行真正的天气查询代码。
4. **二次调用 (Second LLM Call)：** 将查询到的天气数据以“工具结果”的身份再次发给大模型，让它总结成自然语言回复给用户。

```javascript
// 天气获得智能体
import OpenAI from "openai";

const openai = new OpenAI({
    baseURL: 'https://api.deepseek.com',
    apiKey: process.env.DEEPSEEK_API_KEY,
});

const getWeatherTool = JSON.stringify({
    type: 'function',
    function: {
        name: 'getWeather',
        description: '获取指定城市的当天天气情况，当问到天气时调用这个接口',
        parameters: {
            type: 'object',
            properties: {
                city: {
                    type: 'string',
                    description: '城市名称不带市、区',
                },
            },
            required: ['city'],
        },
    }
});
const tools = [JSON.parse(getWeatherTool)];

async function getWeather(city) {
    console.log(`本地代码运行中...... 正在查询${city}天气接口`);
    const cleanCity = city.replace(/[市区]$/, '');
    const url = `http://v1.yiketianqi.com/free/day?appid=59483788&appsecret=DG1LdaOM&unescape=1&city=${cleanCity}`;
    const response = await fetch(url);
    const data = await response.json();

    // 【优化】直接将模型需要的数据转成字符串返回，降低本地模型的理解难度
    return JSON.stringify({
        weather: data,
    });
}

async function getLlmResponse(messages) {
    const response = await openai.chat.completions.create({
        messages,
        model: 'deepseek-chat',
        tools,
    });
    return response.choices[0].message;
}

// 判断是否工具调用，是返回第一个工具调用函数
function isToolCall(message) {
    const { tool_calls } = message;
    if (
        Array.isArray(tool_calls) &&
        tool_calls.length > 0
    ) {
        return {
            toolName: tool_calls[0].function.name,
            arguments: JSON.parse(tool_calls[0].function.arguments),
            toolCallId: tool_calls[0].id,
        };
    }
    return null;
}

async function main(prompt) {
    const messages = [{
        role: 'system',
        content: '你是一个贴心的智能天气助手。判读用户如果有对天气的问询，调用工具，请根据工具返回的数据，用自然流畅、易于理解的语言为用户总结当天的天气情况。',
    }];
    messages.push({
        role: 'user',
        content: prompt,
    });
    const response = await getLlmResponse(messages);
  	// 重要deepseek 的tool 必须跟在 tool_calls后边
    messages.push(response);
    const toolObject = isToolCall(response);
    if (toolObject) {
        const { toolName, arguments: toolArguments, toolCallId } = toolObject;
        if (toolName === 'getWeather') {
            const { city } = toolArguments;
            const weather = await getWeather(city);
            messages.push({
                role: 'tool',
                tool_call_id: toolCallId,
                name: toolName,
                content: weather,
            });
            const userResponse = await getLlmResponse(messages);
            console.log('输出：', userResponse.content);
        } else {
            console.log('输出：模型报错，不支持工具调用');
        }
    } else {
        console.log('输出：', response.content);
    }
}

// const prompt = '今天北京天气怎么样？';
const prompt = '如果南京今天晚上温度在10度以上的话，我就出去玩';
main(prompt);
```

MCP 的核心架构

MCP 采用了非常经典的 Client-Server（客户端-服务端）架构。当你构建一个应用时，它的运转逻辑是这样的：

1. **MCP Host (宿主程序):** 你的大模型应用本身（比如你用 Vercel AI SDK 或 LangGraph 写的 Node.js 后端程序，或是类似 Claude Desktop 的桌面应用）。
2. **MCP Client (客户端):** 运行在宿主程序内部，负责和外部通信。它维持与服务端的双向连接，并在 Agent 需要时向服务端发送标准的 JSON-RPC 请求。
3. **MCP Server (服务端):** 独立的轻量级程序，真正负责与特定的数据源或 API 交互。例如，你可以有一个专门连接 GitHub API 的 MCP Server，或者一个专门读取本地数据库的 MCP Server。

MCP Server 能提供什么？

一个标准的 MCP Server 可以在三个维度上为你的 Agent 提供能力支持：

- **Resources (资源 - 静态读取):** 让大模型读取外部系统中的数据（就像给了 LLM 文件的读取权限）。比如直接读取本地的代码仓库、Slack 聊天记录或者 Notion 文档。
- **Tools (工具 - 动态执行):** 就是你之前了解的 Function Calling 的标准化版本。允许大模型执行动作，比如“在 GitHub 上创建一个 Issue”、“查询天气”或“执行一段 SQL 语句”。
- **Prompts (提示词模板):** 服务端可以提供预设的、带有上下文的提示词模板，让宿主程序直接调用，简化复杂的 Prompt 工程。

## ReAct规范

如果说工具调用是agent的手，那么ReAct就是指导手配合大脑工作的神经系统。ReAct并不是一个可以直接`npm install`的代码库，是一篇由普林斯顿大学和Google在2022年提出的提示词工程规范，全程是`Reasoning and Acting(推理与行动)`。

简单来说：它强制要求大模型在采取任何行动前，必须大声把思考过程说出来。

`ReAct`将思考与行动结合起来，并允许获取外部信息，首先思考，再行动，然后观察行动结果来进行下一步思考。

## 知识图谱

什么是知识图谱：

知识图谱是以图论的形式表达事物之间关系的数据库。



知识图谱由三个基本构件组成：实体（节点），关系（边），属性

例如：

```json
const knowledgeGraph = {
  nodes: [
    { id: "e1", label: "Person", name: "尤雨溪" },
    { id: "e2", label: "Framework", name: "Vue.js", version: "3.x" },
    { id: "e3", label: "Language", name: "TypeScript" }
  ],
  edges: [
    { source: "e1", target: "e2", type: "CREATED" },
    { source: "e2", target: "e3", type: "WRITTEN_IN" }
  ]
};
```



知识图谱是不同于关系数据库、向量数据库的一种数据库形式。

- **向量搜索的盲区：** 如果你问“尤雨溪创造的那个框架是用什么语言写的？”，向量搜索可能因为文本块切割的问题，找不全这些跨度很大的信息，导致 AI 胡说八道。向量数据库不善于复杂的推理。
- **知识图谱的绝杀（GraphRAG）：** 现在的 AI 应用开始走向 **GraphRAG（图检索增强生成）**。当 AI 拿到问题后，它会在知识图谱里进行图遍历（Graph Traversal）。
  1. 找到节点 `[尤雨溪]`
  2. 顺着 `[CREATED]` 关系找到节点 `[Vue.js]`
  3. 顺着 `[WRITTEN_IN]` 关系找到节点 `[TypeScript]`
  4. 把这条精准的链路交给大模型，大模型就能百分之百准确地回答问题。



LangGraph & 知识图谱：

+ LangGraph是一个控制流逻辑图，是觉得agent应该做什么，应该调用什么工具
+ 知识图谱是一个数据存储图，适合用于作为agent的记忆库，帮助ai更准确获得数据库层技术

## 流程编排与架构

在agent调用工具有几种方式

1. 静态预定义（最常见）：初级的agent会实现定义好tool函数的描述和JSON Schema，每次调用LLM时，会把这些塞进上下文中，但是上下文窗口有限，随着工具的增多会塞不进去。
2. 动态检索与挂载：处理大量工具的主流方案，工具一开始并不需要全给LLM，而是通过检索动态获取
   1. 把所有可用工具存入向量数据库中
   2. 当用户输入问题
   3. 系统用用户输入的问题去向量数据库做相似检索
   4. 检索出最匹配的 3 个工具（比如 `getStockPrice`, `getMarketNews`）
   5. 系统**只把这 3 个工具**的定义临时发给 LLM，让 LLM 决定调用哪一个。

3. 自主创建与执行：这是agent最高级的能力，工具甚至不需要事先存在。用户提出一个需求，agent发现自己的工具库里没有这个能力，会临时写一段代码，在一个安全的环境里执行这段代码，返回这个结果。在这里工具是被临时捏出来的。



有向无环图/循环图的架构？在现代AI工作流和智能体开发中，有向无环图（DAG）/循环图（RAG）是一种非常核心的架构思想。通过将复杂的业务逻辑拆解为图的结构，我们可以清晰地管理执行流程、状态流转以及复杂的循环纠错机制。

在工作流中，图的核心组成部分可以这样理解：

- **节点 (Nodes)**：代表具体的**执行动作**。例如：从数据库检索（Retrieve）、调用大语言模型（LLM Call）、格式化输出等。
- **边 (Edges)**：代表**路由或条件分支**。决定了当前节点执行完毕后，下一步应该去向哪个节点。



为什么要使用有向无环图/循环图？

相比较于通过while if else 控制，使用DAG或RAG有如下好处：

1. 条件清晰，可预测性，避免陷入死循环，可以并行处理任务。
2. 循环图可以帮助实现ReAct模式，反思，处理长程多步任务



### DAG

有向无环图有两点铁律？

1. 有向：节点之间的都是有方向的，节点A指向B，意味着B依赖着A，A不依赖于B
2. 无环：顺着箭头的方向走，永远无法回到已经访问过的节点。



为了实现和操作DAG，需要引入两个重要属性？

1. 入度（In-degree）：有多少条边指向该节点。入度为0的点，意味着他没有任何前置依赖，可以直接执行。
2. 出度（Out-degree）：该节点指向多少其他节点。

### thinking in langgraph

langgraph官方推荐步骤：

LangGraph 智能体构建标准五步法

1. **将工作流拆解为离散的步骤 (Map out workflow as discrete steps)**
   * 在编写代码前，先梳理业务流程并绘制出流程图。
   * 将整个复杂任务拆解为多个独立的“节点 (Nodes)”，每个节点只负责完成一件具体的事情（例如：读取输入、意图分类、搜索文档等）。
   * 细化节点的优势：实现更细粒度的断点容错（Checkpoint），并在出错时无需从头开始；同时大幅提升图执行过程的可观测性。

2. **识别每个节点的类型与职责 (Identify what each step needs to do)**
   * 为第一步拆解出的每个节点明确其功能定位：
     * **LLM 步骤**：依赖大模型进行理解、推理、分析或生成文本。
     * **数据步骤 (Data)**：从外部知识库、数据库或内部系统检索/查询信息。
     * **动作步骤 (Action)**：执行对外的实质性操作（如发送邮件、写入数据库、创建工单）。
     * **用户输入步骤 (User Input)**：需要人工介入审核、确认或补充信息。

3. **设计全局状态 (Design your state)**
   * 状态 (State) 是整个图中所有节点共享的“数据黑板”与记忆中枢。
   * **只存储必要数据**：只有必须跨节点流转、后续节点强依赖的数据才存入 State。能通过现有数据推导出来的就不要存。
   * **核心原则**：State 中应该**只保存“原始结构化数据”**（如原始 JSON 字段、枚举值），绝对不要直接保存格式化拼接好的 Prompt 字符串。Prompt 的组装应该放在节点内部按需进行。

4. **构建节点函数与异常处理 (Build your nodes and handle errors)**
   * 将每一个节点实现为纯 JavaScript/TypeScript 函数，该函数接收当前 State 并返回需要更新的 State 增量。
   * 在节点内部建立完善的异常处理机制：
     * **瞬态错误**（网络抖动、API 限流）：通过框架层配置 `retryPolicy` 自动进行指数退避重试。
     * **LLM 可恢复错误**（工具参数错误、格式错误）：捕获异常并存入 State，利用条件边将图路由回 LLM 节点，让模型根据报错信息“自我反省”并重新输出。
     * **用户干预错误**（信息不足、需二次确认）：使用 `interrupt()` 暂停当前执行流，等待人在回路 (Human-in-the-loop) 补全信息。

5. **组装连线并编译执行 (Wire it together and compile)**
   * 使用 `StateGraph` 类将之前定义的 State 结构和 Nodes 函数组装起来。
   * 使用 `addEdge` 建立确定的线性流转路径（如：步骤 A 必定走到步骤 B）。
   * 使用 `addConditionalEdges` 编写条件路由逻辑，让智能体具备动态决策能力（例如：根据意图分类的结果，决定下一步是走查数据库节点，还是走人工审核节点）。
   * 连通图的 `START` 和 `END` 节点后，调用 `.compile()` 完成编译，生成最终的 AI 工作流。

### 常见的工作流编排模式 & 从工作流走向智能体

langgraph总结了常见的五种工作流编排方式：

#### prompt chaining

提示词链是一种将复杂任务拆分成多个小的、可验证的步骤，上一节点llm的输出是下一节点llm的输入。

适用于明确的可拆解的任务，比如翻译->校验->润色。

以一个生成七言诗为例，要求有意象构建、借景抒情的思想

```typescript
import type { GraphNode, ConditionalEdgeRouter } from '@langchain/langgraph';
import { END, START, StateSchema, StateGraph, MessagesValue } from '@langchain/langgraph';
import { ChatDeepSeek } from '@langchain/deepseek';
import { SystemMessage, HumanMessage } from '@langchain/core/messages';
import * as z from 'zod';

const suggestionSchema = z.object({
    isNeedImpove: z.boolean().describe('是否需要改进'),
    updateSuggestion: z.string().describe('改进建议'),
});

const PeomState = new StateSchema({
    messages: MessagesValue,
    topic: z.string(),
    initPeom: z.string(),
    suggestion: suggestionSchema,
    improve: z.string(),
});

const model = new ChatDeepSeek({
    model: 'deepseek-chat',
    apiKey: process.env.DEEPSEEK_API_KEY,
});

const generatePeom: GraphNode<typeof PeomState> = async (state) => {
    const response = await model.invoke([
        new SystemMessage('你是一个诗人，擅长写古代的七言绝句。'),
        new HumanMessage(`生成一首七言诗，主题是: ${state.topic}`),
    ]);
    return {
        initPeom: String(response.content),
        messages: [response],
    };
}

const improvePeom: GraphNode<typeof PeomState> = async (state) => {
    const modelWithStructure = model.withStructuredOutput(suggestionSchema);
    const response = await modelWithStructure.invoke(`判断以下诗中是否有意象构建、借景抒情的手法，没有的话给出改进建议，诗歌如下所示：${state.initPeom}`);
    return {
        suggestion: response,
        messages: [response],
    }
}

const updatePeom: GraphNode<typeof PeomState> = async (state) => {
    const response = await model.invoke([
        new SystemMessage('你是一个诗人，擅长写古代的七言绝句。'),
        new HumanMessage(`根据以下建议，修改诗歌：${state.suggestion?.updateSuggestion || ''}`),
    ]);
    return {
        improve: String(response.content),
        messages: [response],
    };
}

const shouldContinue: ConditionalEdgeRouter<typeof PeomState, Record<string, unknown>, 'updatePeom'> = async (state) => {
    const { suggestion } = state;
    if (!suggestion?.isNeedImpove) {
        return END;
    }
    return 'updatePeom';
}

const agent = new StateGraph(PeomState)
    .addNode('generatePeom', generatePeom)
    .addNode('improvePeom', improvePeom)
    .addNode('updatePeom', updatePeom)
    .addEdge(START, 'generatePeom')
    .addConditionalEdges('improvePeom', shouldContinue, ['updatePeom', END])
    .addEdge('updatePeom', 'improvePeom')
    .compile();

const result = await agent.invoke({
    topic: '枯竭的溪流',
});

for (const message of result.messages) {
    console.log(`[${message.type}]: ${message.content}`);
}

```

#### 并行化 (Parallelization)

让 LLM 同时执行多个任务。这不仅能提升运行速度，还能用于对比验证输出。

- **适用场景**：
  - **分工协作（提速）**：同时执行相互独立的子任务（比如同时生成一个主题的笑话、故事和诗歌，最后聚合）。
  - **多方评估（提质）**：用不同的评估标准（如引用数量、来源质量）同时去打分，增加最终结果的可信度。
- **LangGraph 实现**：`START` 节点同时连接到多个 Node，这几个 Node 随后再同时连接到一个 `Aggregator` (聚合节点) 汇总状态。

```typescript
import { StateGraph, StateSchema } from "@langchain/langgraph";
import { ChatDeepSeek } from "@langchain/deepseek";
import type { GraphNode } from "@langchain/langgraph";
import * as z from "zod";

// Graph state
const State = new StateSchema({
  topic: z.string(),
  joke: z.string(),
  story: z.string(),
  poem: z.string(),
  combinedOutput: z.string(),
});

const llm = new ChatDeepSeek({
  model: "deepseek-chat",
  apiKey: process.env.DEEPSEEK_API_KEY,
});

// Nodes
// First LLM call to generate initial joke
const callLlm1: GraphNode<typeof State> = async (state) => {
  const msg = await llm.invoke(`Write a joke about ${state.topic}`);
  return { joke: String(msg.content) };
};

// Second LLM call to generate story
const callLlm2: GraphNode<typeof State> = async (state) => {
  const msg = await llm.invoke(`Write a story about ${state.topic}`);
  return { story: String(msg.content) };
};

// Third LLM call to generate poem
const callLlm3: GraphNode<typeof State> = async (state) => {
  const msg = await llm.invoke(`Write a poem about ${state.topic}`);
  return { poem: String(msg.content) };
};

// Combine the joke, story and poem into a single output
const aggregator: GraphNode<typeof State> = async (state) => {
  const combined = `Here's a story, joke, and poem about ${state.topic}!\n\n` +
    `STORY:\n${state.story}\n\n` +
    `JOKE:\n${state.joke}\n\n` +
    `POEM:\n${state.poem}`;
  return { combinedOutput: combined };
};

// Build workflow
const parallelWorkflow = new StateGraph(State)
  .addNode("callLlm1", callLlm1)
  .addNode("callLlm2", callLlm2)
  .addNode("callLlm3", callLlm3)
  .addNode("aggregator", aggregator)
  .addEdge("__start__", "callLlm1")
  .addEdge("__start__", "callLlm2")
  .addEdge("__start__", "callLlm3")
  .addEdge("callLlm1", "aggregator")
  .addEdge("callLlm2", "aggregator")
  .addEdge("callLlm3", "aggregator")
  .addEdge("aggregator", "__end__")
  .compile();

// Invoke
const result = await parallelWorkflow.invoke({ topic: "cats" });
console.log(result.combinedOutput);
```

#### 路由 (Routing)

接收输入后，使用 LLM 或规则分析上下文，然后将任务分发给专门的子流程（节点）去处理。

- **适用场景**：分类处理复杂请求（如：客服系统先判断是“退款”、“咨询”还是“投诉”，然后走不同的处理逻辑）。
- **LangGraph 实现**：使用 `Structured Output` (结构化输出) 强迫大模型输出一个决策枚举值，然后用 `addConditionalEdges` (条件边) 根据这个值决定下一步走向 Node A, B 或 C。

#### 编排者-工作者 (Orchestrator-Worker)

这是处理动态、不确定数量子任务的高级模式。**编排者 (Orchestrator)** 负责将大任务分解为多个子任务，并分配给**工作者 (Workers)**；工作者并行执行后，结果再汇总回来。

- **适用场景**：任务数量动态变化的情况（如：写一份代码，需要分别修改 N 个不同的文件，N 是未知的）。
- **LangGraph 实现核心技术**：使用 **`Send` API**。通过条件路由，返回一个 `Send("节点名称", 状态)` 的数组，LangGraph 会根据数组长度自动动态生成（克隆）并启动对应数量的 Worker 节点。

#### 评估者-优化者 (Evaluator-Optimizer)

引入了“自我纠错”循环。一个 LLM 负责生成内容，另一个 LLM（或人工）负责评估；如果不达标则提供反馈并打回重做，直到满足条件。

- **适用场景**：有明确的成功标准，但很难一次性做对的任务（如：精准翻译、代码生成、根据特定格式写文章）。
- **LangGraph 实现**：构建一个**循环 (Cycle)**。生成节点 (Generator) 连向评估节点 (Evaluator)，评估节点通过条件边判断：如果合格则走向 `END`，如果不合格则带上反馈 (Feedback) 连回生成节点。

#### 真正的智能体 (Agents)

文档最后指出，上述 5 种更多偏向于“被我们预先设计好轨道”的**工作流**。

真正的 **Agent 模式** 是基于工具调用 (Tool Calling) 的持续反馈循环。在 Agent 模式下：

1. LLM 被赋予了一组工具。
2. 它每次都在一个 `while` 循环里思考：“我现在应该直接回答用户，还是调用某个工具？”
3. 调用工具后，拿到观察结果，再继续思考下一步。 这种模式解决问题的路径是不可预测的，赋予了 LLM 最高的自主性，LangGraph 中的经典 `createReactAgent` 就是这种模式的封装。

#### 对于真正智能体的评价

`”对于按照工作流编排写出来的程序算智能体?“`

这是一个ai圈中争论很激烈的点。



按自主化程度来分，可以分为以下三类：

1. 完全写死的工作流编排，0%路由自主权，完全按照写死的路径执行，比如提示词链，翻译->校验->润色
2. 50%的路由自主权，这是目前工业界最成熟、落地最多的模式，比如router、Evaluator-Optimizer 模式，大模型有一定权利决定去走哪几条路，或者是否需要返回去重做。但是大模型的想象力被限制在了langgraph定义好的图里。
3. 纯智能体，100%路由自主权，开发者给大模型一个目标，以及一堆工具，大模型自己在一个无限的 `while` 循环里去思考、规划、调用工具，直到它自己觉得做完了为止。毫无疑问是智能体，但是在真实生产环境中，往往最不可控，最容易陷入幻觉和循环之中。



+ 通常来说，完全写死的工作流不算真正的智能体，但现实中，绝大多数优秀的AI落地，都处于两者的灰色地带，通常被称为智能体化工作流(agentic workflow)
+ 市面上很多被称为Agent的产品，扒开一看都是写死的工作流，这其实是营销的术语。正如吴恩达强调，不要过分追求打造一个全知全能的 Pure Agent，未来的趋势是 Agentic Workflow，像 Cursor 这样极其成功的产品，也是把大模型的自主权“关进”了 Plan-and-Execute 的工作流笼子里。开发者设定了“先生成计划 -> 再逐个执行计划 -> 如果报错就看日志修复”这个死框架，以此来保证大模型不会“脱缰”。
+ 所以只要在流程中把部分或者全部的控制权交给大模型，就可以称为智能体，或者智能体化工作流

### 持久化persistence

langgraph内置了一个持久化层，可将图的状态保存为**检查点（checkpoints）**。当你使用 **Checkpointer（检查点保存器）编译**图时，系统会在执行的每一个步骤保存一个图状态的快照（snapshot），并按线程（threads）进行组织管理。这一机制使得**人在回路（human-in-the-loop）工作流**、**对话记忆（conversational memory）**、**时间旅行调试（time travel debugging）**以及**容错执行（fault-tolerant execution）**成为可能。



![Checkpoints](/Users/chenhao/code/study_md/${image}/checkpoints.jpg)

上边的图片讲述了持久化的过程，描述了持久化过程中的几个节点和概念：

+ Super-steps：超级步，langgraph会在super-steps后进行状态快照，保存状态，每一个顺序执行的节点被称为超级步，如果这个阶段时并行执行的，他们被称为一个超级步，状态会在他们都执行完成后进行结算。
+ checkpoints：检查点，保存系统状态，包括state、next(下一个执行的点，是断电恢复的关键)、id等
+ Thread：线程，检查点的集合，这是为什么需要传thread_id，因为一个thread_id可以把这次的历史checkpoints串联起来，形成记忆链条。
+ Statesnapshot: 是 TypeScript/代码层面的类型定义。当调用 `graph.getState()` 时，返回的具体数据对象类型就是 `StateSnapshot`。

#### 为什么需要持久化

是实现以下功能必备；

+ Human-in-the-loop: 允许人去检查、终端、通过图的阶段，这样的工作流就需要检查点机制，让人可以算是查看各阶段的状态，以及恢复相应的状态。
+ Memory: 检查点支持交互之间的记忆，当有重复的人类交互（比如对话）中，我门可以把新的消息插入到线程之中，并保留之前线程中交互的记忆。
+ Time travel：检查点机制（Checkpointers）允许进行“时间旅行”，使用户能够重播（replay）此前的图执行过程，从而回顾和/或调试特定的执行步骤。此外，检查点机制还使得在任意检查点对图状态进行分叉（fork）成为可能，以便探索其他的执行路径（替代轨迹）。
+ Fault tolerance：容错性，如果一个超级步中的一个或者几个节点发生错误，就可以回退到最新的一个节点重新执行。
+ Pending write: 当图节点在某个超级步骤执行过程中失败时，LangGraph 会存储该超级步骤中其他成功完成节点的待处理检查点写入。当您从该超级步恢复图执行时，无需重新运行已成功的节点。

```typescript
  foo: z.string(),

    z.array(z.string()).default(() => []),
    {
      inputSchema: z.array(z.string()),
      reducer: (x, y) => x.concat(y),
    }
  ),
});
```

##### update state

可以使用 `graph.updateState()` 编辑图状态。这会创建一个包含更新值的新检查点，而不会修改原始检查点。更新操作的处理方式与节点更新相同：当定义了归约函数时，值会通过这些函数传递，因此带有归约器的通道会累积值而非覆盖它们。

##### Memory store

State schema会存储一系列key，在图执行过程中，checkpoints会填充这些key，这样实现了状态持久化。但是线程之间还需要保留信息，比如一个聊天机器人，希望所有的聊天记录保留用户信息。

##### 检查点库

langgraph的检查点功能由符合 `BaseCheckpointSaver` 接口的检查点对象驱动。LangGraph 提供了多种检查点实现，均通过独立、可安装的库来实现。

+ `@langchain/langgraph-checkpoint` ：检查点保存器（ `BaseCheckpointSaver` ）和序列化/反序列化接口（ `SerializerProtocol` ）的基础接口。包含用于实验的内存检查点实现（ `MemorySaver` ）。LangGraph 内置了 `@langchain/langgraph-checkpoint` 。
+ `@langchain/langgraph-checkpoint-sqlite` ：一种使用 SQLite 数据库（ `SqliteSaver` ）的 LangGraph 检查点实现。适用于实验和本地工作流。需要单独安装。
+ `@langchain/langgraph-checkpoint-postgres` ：一种使用 PostgreSQL 数据库（ `PostgresSaver` ）的高级检查点管理器，用于 LangSmith。非常适合在生产环境中使用。需要单独安装。
+ `@langchain/langgraph-checkpoint-mongodb` ：一种使用 MongoDB 数据库（ `MongoDBSaver` ）的高级检查点管理器。非常适合在生产环境中使用。需要单独安装。
+ `@langchain/langgraph-checkpoint-redis` ：一个使用 Redis 数据库（ `RedisSaver` ）的高级检查点工具。非常适合在生产环境中使用。需要单独安装。

每个检查点器都遵循 `BaseCheckpointSaver` 接口并实现以下方法：

- `.put` - Store a checkpoint with its configuration and metadata.
  `.put` - 存储检查点及其配置和元数据。
- `.putWrites` - Store intermediate writes linked to a checkpoint (i.e. [pending writes](https://docs.langchain.com/oss/javascript/langgraph/persistence#pending-writes)).
  `.putWrites` - 存储与检查点关联的中间写入（即待处理写入）。
- `.getTuple` - Fetch a checkpoint tuple using for a given configuration (`thread_id` and `checkpoint_id`). This is used to populate `StateSnapshot` in `graph.getState()`.
  `.getTuple` - 根据给定配置（ `thread_id` 和 `checkpoint_id` ）获取检查点元组。此操作用于填充 `graph.getState()` 中的 `StateSnapshot` 。
- `.list` - List checkpoints that match a given configuration and filter criteria. This is used to populate state history in `graph.getStateHistory()`
  `.list` - 列出与给定配置和筛选条件匹配的检查点。这用于在 `graph.getStateHistory()` 中填充状态历史记录。

### Durable execution 持久化执行

持久化执行是一个技术，可以保存工作流节点进度，可以使其暂时中断，并且能够精准恢复，用户在回路中可以通过暂停，检查、验证、修改任务，并且在遇到错误时或者长时间任务，通过保留工作，可以使流程从某一点开始，而之前的任务不用再重复执行。



这就对我们设计的agent或者图功能有需求

1. 有checkpointer启用持久化
2. 在使用checkpointer的情况下，使用线程id，来保存特定的实例
3. 将所有非确定性操作（例如随机数生成）或具有副作用操作（例如文件写入、API 调用）封装在任务内部，以确保当工作流恢复时，这些操作不会在特定运行中重复执行，而是从持久层检索其结果。且尽量不要将有多个副作用的操作放在一个节点，将每个操作封装在单独的任务中，这样可以减少重复工作。

#### 持久化模式

LangGraph 支持三种持久性模式，允许您根据应用程序需求在性能和数据一致性之间取得平衡。较高的持久性模式会增加工作流执行的开销。我们可以在调用任何图形执行方法时指定持久性模式：

```typescript
await graph.stream(
  { input: "test" },
  { durability: "sync" }
)
```

从最不持久到最持久，依次如下：

+ `exit`：LangGraph 仅在图形执行成功退出、出错或因人工干预中断时才会持久化更改。这为长时间运行的图形提供了最佳性能，但也意味着中间状态不会被保存，因此无法从执行过程中发生的系统故障（如进程崩溃）中恢复。
+ `async`： LangGraph 在下一步执行时异步持久化更改。这提供了良好的性能和持久性，但如果进程在执行过程中崩溃，LangGraph 存在一个很小的风险，即不会写入检查点。
+ `sync`：LangGraph 在下一步开始前同步持久化变更。这确保了 LangGraph 在继续执行前写入每个检查点，以一定的性能开销为代价提供了高持久性。

#### 恢复工作流

开启持久化后一下的场景可以恢复工作流

+ `Pausing and Resume Workflow`
+ `Recovering from Failures`，在发生异常（例如 LLM 服务提供商中断）后，自动从最后一个成功的检查点恢复工作流。但需要注意的是需要提供null作为输入值，要不然重启后task会都重新执行一次。



​	`Recovering from Failures`

```typescript
import { entrypoint, task, MemorySaver } from "@langchain/langgraph";

// This variable is just used for demonstration purposes to simulate a network failure.
// It's not something you will have in your actual code.
let attempts = 0;

const getInfo = task("getInfo", async () => {
  /**
   * Simulates a task that fails once before succeeding.
   * Throws an exception on the first attempt, then returns "OK" on subsequent tries.
   */
  attempts += 1;

  if (attempts < 2) {
    throw new Error("Failure"); // Simulate a failure on the first attempt
  }
  return "OK";
});

// Initialize an in-memory checkpointer for persistence
const checkpointer = new MemorySaver();

const slowTask = task("slowTask", async () => {
  /**
   * Simulates a slow-running task by introducing a 1-second delay.
   */
  await new Promise((resolve) => setTimeout(resolve, 1000));
  console.log('Ran slow task.');
  return "Ran slow task.";
});

const main = entrypoint(
  { checkpointer, name: "main" },
  async (inputs: Record<string, any>) => {
    /**
     * Main workflow function that runs the slowTask and getInfo tasks sequentially.
     *
     * Parameters:
     * - inputs: Record<string, any> containing workflow input values.
     *
     * The workflow first executes `slowTask` and then attempts to execute `getInfo`,
     * which will fail on the first invocation.
     */
    const slowTaskResult = await slowTask(); // Blocking call to slowTask
    await getInfo(); // Exception will be raised here on the first attempt
    console.log('Main workflow completed.');
    return slowTaskResult;
  }
);

// Workflow execution configuration with a unique thread identifier
const config = {
  configurable: {
    thread_id: "1", // Unique identifier to track workflow execution
  },
};

// This invocation will take ~1 second due to the slowTask execution
try {
  // First invocation will raise an exception due to the `getInfo` task failing
  await main.invoke({ any_input: "foobar" }, config);
} catch (err) {
  // Handle the failure gracefully and retry the same thread.
  console.log("err has occurred, this info is:", err);
  const resumed = await main.invoke(null, config);
}
```

#### Starting points for resuming workflows

- If you’re using a [StateGraph (Graph API)](https://docs.langchain.com/oss/javascript/langgraph/graph-api), the starting point is the beginning of the [**node**](https://docs.langchain.com/oss/javascript/langgraph/graph-api#nodes) where execution stopped.
  如果您使用的是 StateGraph（图 API），起始点将是执行停止的节点开始处。
- If you’re making a subgraph call inside a node, the starting point will be the **parent** node that called the subgraph that was halted. Inside the subgraph, the starting point will be the specific [**node**](https://docs.langchain.com/oss/javascript/langgraph/graph-api#nodes) where execution stopped.
  如果您在节点内部调用子图，起始点将是调用被中断子图的父节点。在子图内部，起始点将是执行停止的具体节点。
- If you’re using the Functional API, the starting point is the beginning of the [**entrypoint**](https://docs.langchain.com/oss/javascript/langgraph/functional-api#entrypoint) where execution stopped.
  如果您使用的是函数式 API，起点是执行停止的入口点开始处。

### Streaming 流式输出

为什么大模型有流式输出而图还需要流式输出：

大模型流式输出实现一个打字机效果，告诉用户大模型在输出，而图或者智能体，其执行所需时间更长，如果长时间没有响应，用户可能会认为应用执行失败或者卡死了。

二者输出对比：

| **维度**       | **大模型的流输出 (LLM Streaming)**              | **LangGraph 的流输出 (Graph Streaming)**                     |
| -------------- | ----------------------------------------------- | ------------------------------------------------------------ |
| **颗粒度**     | **极其细微**。每次吐出一个字或一个词（Token）。 | **相对宏观**。每次吐出一个节点执行完毕后的状态（State）或自定义事件。 |
| **输出内容**   | 纯文本字符串（或结构化 JSON 的片段）。          | 整个图的状态对象、工具执行结果、或者是从底层透传上来的大模型 Token。 |
| **解决的问题** | 降低“首字响应时间 (TTFB)”，优化阅读体验。       | 提升整个长工作流的可观测性，提供“进度条”体验。               |

基本使用

```typescript
for await (const chunk of await graph.stream(inputs, {
  streamMode: 'updates',
})) {
  console.log(chunk);
}
```

#### stream mode

| Mode     | Description                                                  |
| -------- | ------------------------------------------------------------ |
| values   | 每一步后的完整状态                                           |
| updates  | 每一步之后都会更新，同一步骤中的多次更新会分别流式传输       |
| Messages | 2-tuples of (LLM token, metadata) from LLM calls.            |
| custom   | 通过 `writer` 配置参数从节点发出的自定义数据。               |
| Tools    | Tool-call lifecycle events (`on_tool_start`, `on_tool_event`, `on_tool_end`, `on_tool_error`). |
| Debug    | All available info throughout graph execution.               |

##### LLM Tokens

如果想实现打字机效果，可以通过设置messages 模式，它不仅能流出状态的改变，更重要的是，它能深挖到图（Graph）的内部，把任意 Node、Tool 或 Subgraph 里 LLM 生成的每一个 Token “透传”出来。

基础用法 (LLM Tokens)

要开启 Token 级的流式输出，你需要在调用 `graph.stream()` 时将 `streamMode` 设置为 `"messages"`。

**返回值结构**： 在 `messages` 模式下，流返回的数据不再是单纯的图状态对象，而是一个包含了两个元素的数组（Tuple / 元组）：`[message_chunk, metadata]`。

- `message_chunk`：大模型吐出的片段（即一个 Token 或一段文本）。
- `metadata`：元数据字典。这是 LangGraph 加的“料”，里面包含了这个 Token 是由哪个图节点（node）调用的、包含了什么标签（tags）等上下文信息。

*（文档还特意指出，即便你在 Node 内部调用 LLM 时用的是 `model.invoke` 而不是 `model.stream`，只要最外层的图用的是 `messages` 模式，LangChain 底层依然会魔法般地帮你把它转成流式输出发射出来。）*

> 需要注意的是大模型的模型调用库需要使用langchain，因为langchain会提供一个回调管理器，langgraph会给把一个监听器绑定到图里所有的 LangChain 模型实例上，这样在调用的时候会获取大模型输出的token。如果我们使用的是openai等其他库的话，需要使用custom模式，给接入到这里边。

```typescript
import 'dotenv/config';
import { ChatDeepSeek } from '@langchain/deepseek';
import { StateGraph, StateSchema, START } from "@langchain/langgraph";
import type { GraphNode } from "@langchain/langgraph";
import * as z from 'zod';

const MyState = new StateSchema({
    topic: z.string(),
    joke: z.string().default(""),
});

const apiKey = process.env.DEEPSEEK_API_KEY;
if (!apiKey) {
    throw new Error('DEEPSEEK_API_KEY is not set. Please check your .env file or shell environment.');
}

const model = new ChatDeepSeek({
    model: 'deepseek-chat',
    apiKey,
});

const callModel: GraphNode<typeof MyState> = async (state) => {
    // Call the LLM to generate a joke about a topic
    // Note that message events are emitted even when the LLM is run using .invoke rather than .stream
    const modelResponse = await model.invoke([
      { role: "user", content: `Generate a joke about ${state.topic}` },
    ]);
    return { joke: modelResponse.content };
};

const graph = new StateGraph(MyState)
  .addNode("callModel", callModel)
  .addEdge(START, "callModel")
  .compile();

for await (const [messageChunk, metadata] of await graph.stream(
    { topic: "ice cream" },
    { streamMode: "messages" }
)) {
    if (messageChunk.content) {
        console.log(messageChunk.content + "|");
    }
}
```

###### 根据大模型调用进行过滤

在一个复杂的图里，我们可能会同时调用好几个不同的大模型（比如一个负责写诗，一个负责讲笑话）。如果你只想把“写诗”的模型输出流到前端，可以这样做：

- **打标签**：在初始化大模型实例时，打上特有的标签，例如：`new ChatOpenAI({ tags: ['poem'] })`。
- **过滤**：在接收流的时候，检查元数据：`if (metadata.tags?.includes("poem"))`，只有匹配了才打印出来。

```typescript
import { ChatOpenAI } from "@langchain/openai";

// model1 is tagged with "joke"
const model1 = new ChatOpenAI({
  model: "gpt-5.4-mini",
  tags: ['joke']
});
// model2 is tagged with "poem"
const model2 = new ChatOpenAI({
  model: "gpt-5.4-mini",
  tags: ['poem']
});
```

###### Omit messages from the stream 从流中剔除消息

如果图里有一个节点是让大模型做“内部总结”或“结构化数据提取”，你不希望这些“碎碎念”或者 JSON 代码流到用户前端界面。

- **做法**：给那个内部大模型打上一个特殊的官方内置标签：`tags: ["nostream"]`。
- **效果**：这个大模型依然会正常运行并产出结果存入 State，但它的 Token **绝对不会**出现在 `"messages"` 的流通道中

```typescript
const streamModel = new ChatAnthropic({ model: "claude-3-haiku-20240307" });
const internalModel = new ChatAnthropic({
  model: "claude-3-haiku-20240307",
}).withConfig({
  tags: ["nostream"],
});
```

除了给模型打标签，你还可以直接根据“节点名称”来过滤。比如两个节点并发执行，你只想要其中一个节点的 Token。

- **做法**：在接收流时，检查元数据里的 `langgraph_node` 字段：`if (metadata.langgraph_node === "writePoem")`。

```typescript

  { streamMode: "messages" }
)) {

  // to only include the tokens from the specified node

  }
```

###### Custom data

1. Use the `writer` parameter from the `LangGraphRunnableConfig` to emit custom data.

2. Set `streamMode: "custom"` when calling `.stream()` to get the custom data in the stream. You can combine multiple modes (e.g., `["updates", "custom"]`), but at least one must be `"custom"`.

##### Tool progress

给出了如何获取流式传输工具的执行进展。

当你启用 `tools` 流模式时，LangGraph 会在工具的生命周期中发出以下四种事件：

- **`on_tool_start`**：工具开始调用。包含载荷：`name` (工具名), `input` (输入参数), `toolCallId` (工具调用ID)。
- **`on_tool_event`**：工具产生中间进度数据。包含载荷：`name`, `data` (中间数据), `toolCallId`。
- **`on_tool_end`**：工具执行完毕。包含载荷：`name`, `output` (最终输出), `toolCallId`。
- **`on_tool_error`**：工具执行抛出错误。包含载荷：`name`, `error` (错误信息), `toolCallId`。

### 

为了能够发出中间进度事件（`on_tool_event`），你需要将工具函数定义为**异步生成器** (`async function*`)：

- 使用 **`yield`** 关键字来发送中间进度数据（例如：`yield { message: "正在搜索...", progress: 0.5 }`）。
- 使用 **`return`** 来返回工具的最终结果。
- *(注意：如果使用的是普通的返回 Promise 的异步函数，它也是兼容的，但只会触发 `start` 和 `end` 事件，没有中间进度的 `event` 事件。)*



例如：

```typescript
import 'dotenv/config';
import { ChatDeepSeek } from '@langchain/deepseek';
import {
    StateGraph,
    StateSchema,
    START,
    END,
    MessagesValue,
} from '@langchain/langgraph';
import type { ConditionalEdgeRouter, GraphNode } from '@langchain/langgraph';
import { tool } from "@langchain/core/tools";
import { AIMessage, HumanMessage, ToolMessage } from "@langchain/core/messages";
import * as z from 'zod';

const delay = (ms: number) => new Promise((resolve) => setTimeout(resolve, ms));

const getWeather = tool(
    async function* ({ city }) {
        yield {
            message: `开始搜索${city}的天气信息......`,
            processs: '0%',
            values: '',
        };
        const steps = ['20%', '40%', '80%'];
        for (const process of steps) {
            await delay(1500);
            yield {
                message: `正在搜索${city}的天气信息......${process}`,
                processs: process,
                values: '',
            };
        }
        await delay(1500);
        const result = '气温: 20℃, 天气: 晴, 风力: 2级';
        yield {
            message: `搜索${city}的天气信息完成`,
            processs: '100%',
            values: result,
        };
        return result;
    },
    {
        name: 'getWeather',
        description: '获取指定城市的当天天气情况',
        schema: z.object({
            city: z.string().describe('城市名称'),
        }),
    }
);

const toolsByName: Record<string, typeof getWeather> = {
    [getWeather.name]: getWeather,
};

const model = new ChatDeepSeek({
    model: 'deepseek-chat',
    apiKey: process.env.DEEPSEEK_API_KEY,
});

const modelWithTools = model.bindTools([getWeather]);

const MyState = new StateSchema({
    messages: MessagesValue,
});

const llmCall: GraphNode<typeof MyState> = async (state) => {
    const response = await modelWithTools.invoke(state.messages);
    return { messages: [response] };
};

const toolNode: GraphNode<typeof MyState> = async (state) => {
    const lastMessage = state.messages.at(-1);
    if (!lastMessage || !AIMessage.isInstance(lastMessage)) {
        return { messages: [] };
    }

    const results: ToolMessage[] = [];
    for (const toolCall of lastMessage.tool_calls ?? []) {
        const t = toolsByName[toolCall.name];
        if (!t) continue;
        const observer = await t.invoke(toolCall);
        results.push(observer);
    }
    return { messages: results };
};

const shouldContinue: ConditionalEdgeRouter<
    typeof MyState,
    Record<string, unknown>,
    'toolNode'
> = async (state) => {
    const lastMessage = state.messages.at(-1);
    if (!lastMessage || !AIMessage.isInstance(lastMessage)) {
        return END;
    }
    if (lastMessage.tool_calls?.length) {
        return 'toolNode';
    }
    return END;
};

const graph = new StateGraph(MyState)
    .addNode('llmCall', llmCall)
    .addNode('toolNode', toolNode)
    .addEdge(START, 'llmCall')
    .addConditionalEdges('llmCall', shouldContinue, ['toolNode', END])
    .addEdge('toolNode', 'llmCall')
    .compile();

for await (const chunk of await graph.stream(
    { messages: [new HumanMessage('查询北京的天气情况')] },
    { streamMode: 'tools' },
)) {
    console.log(chunk);
}
```

#### Subgraph outputs 子图输出

要在流式输出中包含子图的输出，您可以在父图的 `.stream()` 方法中设置 `subgraphs: true` 。这将同时流式输出父图和任何子图的输出。

输出将以元组 `[namespace, data]` 的形式流式传输，其中 `namespace` 是一个包含调用子图节点路径的元组，例如 `["parent_node:<task_id>", "child_node:<task_id>"]` 。


### use time-travel 使用时间旅行

time travel，时间旅行需要检查点机制的支持，其有两种模式，一种是`replay`，一种是`fork`。`replay`从某一检查点进行重新执行，之前的节点不会执行，`fork`以修改的状态从检查点开始执行，以探索不同的可能性。

#### Replay 回放

回放要使用先前执行图的配置来重新执行图。

> 重放会重新执行节点——而不仅仅是读取缓存。LLM 调用、API 请求和中断会再次触发，并可能返回不同的结果。从最终检查点（没有 `next` 节点）开始重放是无操作。

使用 `getStateHistory` 找到你想要重放的检查点，然后使用该检查点的配置调用 `invoke` ,参数要传`null`

```typescript
import 'dotenv/config';
import { StateGraph, StateSchema, START, END, MemorySaver } from "@langchain/langgraph";
import type { GraphNode, StateSnapshot } from '@langchain/langgraph';
import { ChatDeepSeek } from '@langchain/deepseek';
import * as z from 'zod';
import { v4 as uuidv4 } from 'uuid';
import { SystemMessage, HumanMessage } from '@langchain/core/messages';

const State = new StateSchema({
    topic: z.string(),
    poem: z.string(),
    externalInfo: z.string(),
    improvePoem: z.string(),
});

const model = new ChatDeepSeek({
    model: 'deepseek-chat',
    apiKey: process.env.DEEPSEEK_API_KEY,
});

const generatePeom: GraphNode<typeof State> = async (state) => {
    const response = await model.invoke([
        new SystemMessage('你是一个诗人，擅长写古代的七言绝句。'),
        new HumanMessage(`生成一首七言诗，主题是: ${state.topic}`),
    ]);
    return {
        poem: String(response.content),
    };
}

const improvePeom: GraphNode<typeof State> = async (state) => {
    const response = await model.invoke([
        new SystemMessage('你是一个诗人，擅长写古代的七言绝句。'),
        new HumanMessage(`根据以下要求，${state.externalInfo}，优化以下诗歌诗歌：${state.poem}`),
    ]);
    console.log('improvePeom--', response.content);
    return {
        improvePoem: String(response.content),
    };
}

const workflow = new StateGraph(State)
    .addNode('generatePeom', generatePeom)
    .addNode('improvePeom', improvePeom)
    .addEdge(START, 'generatePeom')
    .addEdge('generatePeom', 'improvePeom')
    .addEdge('improvePeom', END)

const checkpointer = new MemorySaver();
const graph = workflow.compile({
    checkpointer,
});

const config = {
    configurable: {
        thread_id: uuidv4(),
    },
}

await graph.invoke({
    topic: '枯竭的溪流',
    externalInfo: '这首诗的意境要深远，要表达出对人生的思考，要表达出对自然的敬畏，要表达出对生命的赞美。',
}, config);

for await (let state of graph.getStateHistory(config)) {
    states.push(state);
}

console.log('states--', states);
const beforeImprove = states.find((s) => s.next.includes('improvePeom'));
console.log('beforeImprove--', beforeImprove);

await graph.invoke(null, beforeImprove?.config);
```

#### fork 

fork是通过修改状态从过去的时间点创建新分支，之前的检查点上调用 `update_state` 来创建分支，然后使用 `invoke` 和 `None` 继续执行。

> `update_state` 不会回滚线程。它会从指定点创建一个新的检查点分支，原始执行历史保持不变。也就是说已执行的分支不会发生变化，

```typescript

import { SystemMessage, HumanMessage } from '@langchain/core/messages';

const State = new StateSchema({
    topic: z.string(),
    poem: z.string(),
    externalInfo: z.string(),
    improvePoem: z.string(),
});

const model = new ChatDeepSeek({
    model: 'deepseek-chat',
    apiKey: process.env.DEEPSEEK_API_KEY,
});

const generatePeom: GraphNode<typeof State> = async (state) => {
    const response = await model.invoke([
        new SystemMessage('你是一个诗人，擅长写古代的七言绝句。'),
        new HumanMessage(`生成一首七言诗，主题是: ${state.topic}`),
    ]);
    return {
        poem: String(response.content),

        improvePoem: String(response.content),

    .addNode('generatePeom', generatePeom)
    .addNode('improvePeom', improvePeom)
    .addEdge(START, 'generatePeom')
    .addEdge('generatePeom', 'improvePeom')
```

##### From a specific node

`asNode`

当我们调用`updateState`修改图的状态时，LangGraph会使用某个指定节点的写入器（包括reducers）来应用这些状态值，同时，检查点会记录：是这个特定节点产生了这次的状态更新，并且图的后续执行将从这个节点的后继节点开始恢复。

默认情况下，`LangGraph`会根据检查点的历史版本推段是哪个节点（`asNode`），在大多数情况下自动推断是准确的

什么时候需要显式指定 `asNode`？

在以下三种特殊场景中，你需要通过代码显式地指定 `asNode`：

1. **并行分支（Parallel branches）**：如果多个节点在同一个步骤中并发更新了状态，LangGraph 可能无法确定哪个节点是最后一个执行的（如果不明确指定，可能会抛出 `InvalidUpdateError` 错误）。
2. **无执行历史的场景（No execution history）**：在一个全新的线程（Thread）上直接设置初始状态时（这在编写测试代码时非常常见），因为没有历史记录供 LangGraph 推断。
3. **跳过特定节点（Skipping nodes）**：如果你想欺骗图的执行逻辑，可以把 `asNode` 设置为图中的某一个较晚的节点。这样 LangGraph 会认为这个节点**已经执行过了**，从而直接从它的下一个节点继续运行。

```typescript
// 假设图的执行顺序是: generateTopic -> writeJoke

// 使用 updateState 时，通过 `asNode: "generateTopic"` 来明确告诉系统：
// “把这次状态更新看作是由 generateTopic 节点产生的结果”
// 这样在后续调用 invoke() 继续执行时，会直接从 generateTopic 的下一个节点（也就是 writeJoke）开始运行。
const forkConfig = await graph.updateState(
  beforeJoke.config,
  { topic: "chickens" }, // 修改的状态值
  { asNode: "generateTopic" }, // 明确指定这是来自哪个节点的更新
);
```

#### interrupts 中断

如果我们的图中有中断，终端在时间回溯期间也会被重新触发，包含的中断节点会重新执行，而`interrupt`会暂停以等待新的`Command(resume=)`

```typescript
import { StateGraph, StateSchema, START, END, MemorySaver, interrupt, Command } from "@langchain/langgraph";
import type { StateSnapshot } from '@langchain/langgraph';
import * as z from 'zod';
import { v4 as uuidv4 } from 'uuid';

const state = new StateSchema({
    basic: z.string(),
    pagea: z.string(),
    pageb: z.string(),
    pagec: z.string(),
});

const workflow = new StateGraph(state)
    .addNode('node_pagea', (state) => {
        return {
            pagea: `${state.basic}/pagea`,
        }
    })
    .addNode('node_pageb', (state) => {
        return {
            pageb: `${state.basic}/pageb`,
        }
    })
    .addNode('node_pagec', (state) => {
        const interRes = interrupt({
            question: 'Please select a page',
            detail: state.pagea,
        });
        console.log('interRes--', interRes);
        return {
            pagec: `${state.basic}/pagec`,
        };
    })
    .addEdge(START, 'node_pagea')
    .addEdge('node_pagea', 'node_pageb')
    .addEdge('node_pageb', 'node_pagec')
    .addEdge('node_pagec', END);

const checkpointer = new MemorySaver();
const graph = workflow.compile({
    checkpointer,
});

const config = {
    configurable: {
        thread_id: uuidv4(),
    }
};

await graph.invoke({
    basic: 'https://www.baidu.com',
}, config);

graph.invoke(new Command({ resume: 'resume graph'}), config);

const states: StateSnapshot[] = [];
for await (let state of graph.getStateHistory(config)) {
    states.push(state);
}
const beforePageB = states.find((s) => s.next.includes('node_pageb'));
const result = await graph.invoke(null, (beforePageB as StateSnapshot).config);
graph.invoke(new Command({ resume: 'resume graph2'}), config);

```

##### Multiple Interrupts 多次中断

假如我们的图有多个地方需要中断来收集信息，比如一个多步骤的表格，我们就可以在两个`interrupt`之间`fork`，来给一个新的答案，这样之前的问题就不用回答了

```typescript
// Fork from BETWEEN the two interrupts (after askName, before askAge)
const states = [];
for await (const state of graph.getStateHistory(config)) {
  states.push(state);
}
const between = states.filter((s) => s.next.includes("askAge")).pop();

const forkConfig = await graph.updateState(between.config, { value: ["modified"] });
const result = await graph.invoke(null, forkConfig);
// askName result preserved ("name:Alice")
// askAge pauses at interrupt — waiting for new answer
```

#### Subgraphs 子图

使用子图进行时间旅行取决于子图是否有自己的checkpointer，这决定了子图实现时间旅行的粒度，比如默认情况下，子图会继承父图的checkpointer，父图将子图视为一个单一的超级步骤，整个子图执行过程中仅有一个父级检查点，而从子图执行前的时间进行时间回溯，则会从头重新执行该子图。

默认子图中，无法回溯到节点之间的某个时间点，只能从父级进行时间回溯

```typescript
// Subgraph without its own checkpointer (default)
const subgraph = new StateGraph(StateAnnotation)
  .addNode("stepA", stepA)       // Has interrupt()
  .addNode("stepB", stepB)       // Has interrupt()
  .addEdge(START, "stepA")
  .addEdge("stepA", "stepB")
  .compile();  // No checkpointer — inherits from parent

const graph = new StateGraph(StateAnnotation)
  .addNode("subgraphNode", subgraph)
  .addEdge(START, "subgraphNode")
  .compile({ checkpointer });

// Complete both interrupts
await graph.invoke({ value: [] }, config);
await graph.invoke(new Command({ resume: "Alice" }), config);
await graph.invoke(new Command({ resume: "30" }), config);

// Time travel from before the subgraph
const states = [];
for await (const state of graph.getStateHistory(config)) {
  states.push(state);
}
const beforeSub = states.filter((s) => s.next.includes("subgraphNode")).pop();

const forkConfig = await graph.updateState(beforeSub.config, { value: ["forked"] });
const result = await graph.invoke(null, forkConfig);
// The entire subgraph re-executes from scratch
// You cannot time travel to a point between stepA and stepB
```

##### Access the store inside nodes 节点内部访问存储

如果我们使用store编译了图，langgraph会自动将存储注入到节点函数中，那么在节点就可以使用`runtime`访问

```typescript
import { StateGraph, StateSchema, MessagesValue, GraphNode, START } from "@langchain/langgraph";
import { v4 as uuidv4 } from "uuid";

const State = new StateSchema({
  messages: MessagesValue,
});

const callModel: GraphNode<typeof State> = async (state, runtime) => {
  const userId = runtime.context?.userId;
  const namespace = [userId, "memories"];

  // Search for relevant memories
  const memories = await runtime.store?.search(namespace, {
    query: state.messages.at(-1)?.content,
    limit: 3,
  });
  const info = memories?.map((d) => d.value.data).join("\n") || "";

  // ... Use memories in model call

  // Store a new memory
  await runtime.store?.put(namespace, uuidv4(), { data: "User prefers dark mode" });
};

const builder = new StateGraph(State)
  .addNode("call_model", callModel)
  .addEdge(START, "call_model");
const graph = builder.compile({ store });

// Pass context at invocation time
await graph.invoke(
  { messages: [{ role: "user", content: "hi" }] },
  { configurable: { thread_id: "1" }, context: { userId: "1" } }
);
```

#### Manage short-term memory管理短期记忆

启用短期记忆后，长对话可能超出LLM的上下文窗口，常见的解决措施有：

+ Trim messages： 修建消息，移除前N条或者后N条消息（调用LL M之前）
+ Delete messages: 从langgraph中永久删除消息
+ Summarize messages: 总结消息，对历史中的早起消息进行总结，并用总结替换他们
+ Manage checkpoints ：Manage checkpoints to store and retrieve message history
+ Custom stratagies

##### Trim messages 修剪消息

大多数的LLMs都有最大支持的上下文窗口，决定何时截断消息的一种方法是统计历史消息中的token数量，并在接近该限制时进行截断，langchain中我们可以使用消息修剪工具，指定要从列表中保留的token数量，以及用于处理边界的`strategy`

使用`triMessage`函数

```typescript
import { trimMessages } from "@langchain/core/messages";
import { StateSchema, MessagesValue, GraphNode } from "@langchain/langgraph";

const State = new StateSchema({
  messages: MessagesValue,
});

const callModel: GraphNode<typeof State> = async (state) => {
  const messages = trimMessages(state.messages, {
    strategy: "last",
    maxTokens: 128,
    startOn: "human",
    endOn: ["human", "tool"],
  });
  const response = await model.invoke(messages);
  return { messages: [response] };
};

const builder = new StateGraph(State)
  .addNode("call_model", callModel);
  // ...
```

#### Delete messages 删除消息

我们可以从图状态中删除消息，可以使用`RemoveMessage`，要使其生效，需要使用带有`messagesStateReducer`归约器的状态键，例如`MessageValue`

例如：

```typescript
import { RemoveMessage } from "@langchain/core/messages";

const deleteMessages = (state) => {
  const messages = state.messages;
  if (messages.length > 2) {
    // remove the earliest two messages
    return {
      messages: messages
        .slice(0, 2)
        .map((m) => new RemoveMessage({ id: m.id })),
    };
  }
};
```

#### Summarize messages 总结消息

修剪或删除消息的问题在于，可能会因消息队列而丢失信息，因此，总结消息更适合更复杂的方法。

提示和编排逻辑可用于总结消息历史。例如，在 LangGraph 中，你可以在状态中包含一个 `summary` 键，与 `messages` 键并列：

```typescript
import { StateSchema, MessagesValue, GraphNode } from "@langchain/langgraph";
import { z } from "zod/v4";

const State = new StateSchema({
  messages: MessagesValue,
  summary: z.string().optional(),
});
```

然后，你可以利用现有的任何摘要作为下一次摘要的上下文，生成聊天记录摘要。当 `messages` 状态键中累积了一定数量的消息后，可以调用此 `summarizeConversation` 节点。

```typescript
import { RemoveMessage, HumanMessage } from "@langchain/core/messages";

const summarizeConversation: GraphNode<typeof State> = async (state) => {
  // First, we get any existing summary
  const summary = state.summary || "";

  // Create our summarization prompt
  let summaryMessage: string;
  if (summary) {
    // A summary already exists
    summaryMessage =
      `This is a summary of the conversation to date: ${summary}\n\n` +
      "Extend the summary by taking into account the new messages above:";
  } else {
    summaryMessage = "Create a summary of the conversation above:";
  }

  // Add prompt to our history
  const messages = [
    ...state.messages,
    new HumanMessage({ content: summaryMessage })
  ];
  const response = await model.invoke(messages);

  // Delete all but the 2 most recent messages
  const deleteMessages = state.messages
    .slice(0, -2)
    .map(m => new RemoveMessage({ id: m.id }));

  return {
    summary: response.content,
    messages: deleteMessages
  };
};
```

### Subgraphs 子图

子图是一种作为节点嵌入其他图的图结构

主要有两种用途：

1. 构建多智能体
2. 在多个图中复用同一组节点

3. 分布式开发：当希望不同团队独立处理图的不同部分时，可以将每个部分定义为一个子图。只要子图接口（输入和输出模式）得到遵守，父图就可以在无需了解子图任何细节的情况下构建。

#### Define subgraph communication 定义子图的通信

添加子图时，需要定义父图与子图之间的通信方式。

| Pattern            | When to use                                                  | State schema                                                 |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 在节点内部调用子图 | 父图和子图有不同的state schema，或者我们需要在他们之间转换state | 编写一个包装函数，将父图状态映射到子图输入，并将子图输出映射回父图状态 |
| 将子图作为节点调用 | 父图和子图共享state keys                                     | 可以将编译后的子图直接传给add_node，无需包装函数             |

##### call a subgraph inside a node 在节点内调用子图

当父图和子图具有不同的state schema（无法共享keys）时，在节点函数内调用子图。这在多智能体系统中为每个智能体保留私有消息历史记录时很常见。

节点函数在调用子图之前将父状态转换为子图状态，并在返回之前将结果转换回父状态。

```typescript
import { StateSchema, StateGraph, START } from "@langchain/langgraph";
import * as z from 'zod';

const SubgraphState = new StateSchema({
    bar: z.string(),
});

const subgraphBuilder = new StateGraph(SubgraphState)
    .addNode('subgraphnode', (state) => {
        return {
            bar: 'hi' + `${state.bar}`,
        };
    })
    .addEdge(START, 'subgraphnode')
    
const subgraph = subgraphBuilder.compile();

const State = new StateSchema({
    foo: z.string(),
});

const graphBuilder = new StateGraph(State)
    .addNode('callSubgraph', async (state) => {
        const subgraphOutput = await subgraph.invoke({
            bar: state.foo,
        })
        return {
            foo: subgraphOutput.bar,
        }
    })
    .addEdge(START, 'callSubgraph')

const graph = graphBuilder.compile();

const result = await graph.invoke({
    foo: 'hello',
});
console.log(result.foo);
```

##### add a subgraph as a node 添加子图作为一个节点

当父图与子图共享state keys时，就可以将编译后的子图直接传给add_node，而无需包装函数，多智能体能共享state keys时，智能体通常通过共享的 messages 键进行通信。

我们只需要将编译后的子图传给add_node即可

```typescript
import { StateSchema, StateGraph, START } from "@langchain/langgraph";
import * as z from 'zod';

const MyState = new StateSchema({
    foo: z.string(),
});

const subgraphBuilder = new StateGraph(MyState)
    .addNode('subgraphnode', (state) => {
        return {
            foo: `hi, ${state.foo}`,
        };
    })
    .addEdge(START, 'subgraphnode')
    
const subgraph = subgraphBuilder.compile();

const graphBuilder = new StateGraph(MyState)
    .addNode('callSubgraph', subgraph)
    .addEdge(START, 'callSubgraph');
const graph = graphBuilder.compile();

const result = await graph.invoke({
    foo: 'subgraph'
});

console.log(result);
```

#### Subgraph persistence 子图持久化

使用子图时，需要考虑多次调用的之间的处理方式，以客户支持机器人为例，它会将问题交给专业的子智能体，那么这个子智能体是需要记住用户之前提问的数据还是说会每次重新调用？

根据需求来，langgraph提供了几种子智能体的持久化方案。

通过`.compile()` 上的 `checkpointer` 参数控制子图的持久化：

| Mode 模式                                                    | `checkpointer=`                 | Behavior 行为                                                |
| :----------------------------------------------------------- | :------------------------------ | :----------------------------------------------------------- |
| [Per-invocation 每次调用](https://docs.langchain.com/oss/javascript/langgraph/use-subgraphs#per-invocation-default) | `None` (default)  `None` (默认) | Each call starts fresh and inherits the parent’s checkpointer to support [interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts) and [durable execution](https://docs.langchain.com/oss/javascript/langgraph/durable-execution) within a single call. 每次调用都从全新状态开始，并继承父级的检查点机制，以支持单次调用内的中断和持久化执行。 |
| [Per-thread 每线程](https://docs.langchain.com/oss/javascript/langgraph/use-subgraphs#per-thread) | `True`                          | State accumulates across calls on the same thread. Each call picks up where the last one left off. 状态在同一线程的多次调用间累积。每次调用都从上一次结束的地方继续。 |
| [Stateless 无状态](https://docs.langchain.com/oss/javascript/langgraph/use-subgraphs#stateless) | `False`                         | No checkpointing at all—runs like a plain function call. No interrupts or durable execution. 完全无检查点机制——运行方式如同普通函数调用。不支持中断或持久化执行。 |

每次调用是大多数应用的正确选择，包括子代理处理独立请求的多智能体系统。当子代理需要多轮对话记忆时，使用按线程模式。

##### stateful

有状态子图继承父图的检查点，从而支持中断、持久化执行和状态检查。两种有状态模式的区别在于状态保留时长。

##### per-invocation 每次调用

这是大多数应用推荐使用的模式，包括将子代理作为工具调用的多智能体系统。它支持中断、持久化执行和并行调用，同时保持每次调用的独立性。

当每次对子图的调用相互独立，且子代理无需记忆先前调用信息时，请使用每次调用持久化模式。这是最常见的模式，尤其适用于处理一次性请求（如"查询该客户订单"或"总结此文档"）的多智能体系统。

省略 `checkpointer` 或将其设置为 `None` 。每次调用都会全新开始，但在单次调用过程中，子图会继承父级的检查点器，并可使用 `interrupt()` 实现暂停与恢复。

以下示例使用两个子代理（水果专家、蔬菜专家）作为外层代理的工具进行封装：

```typescript
const veggieTool = tool(
    async (input) => {

}

main();
```

##### per-thread 

当子代理需要记住之前的交互时，使用每线程持久化。例如，一个在多次对话中积累上下文的研究助手，或一个追踪已编辑文件的编程助手。子代理的对话历史和数据会在同一线程的多次调用中累积。每次调用都会从上次中断的地方继续。

使用 `checkpointer=True` 编译以启用此行为。

> 按线程划分的子图并不支持并行工具调用，当 LLM 将按线程划分的子代理作为工具使用时，它可能会尝试并行多次调用该工具（例如，同时向水果专家询问苹果和香蕉的相关信息）这会导致检查点冲突，因为两次调用会写入相同的命名空间。

以下示例使用 LangChain 的 `ToolCallLimitMiddleware` 来避免此问题。如果你使用纯 LangGraph `StateGraph` 进行开发，则需要自行防止并行工具调用——例如，通过配置模型禁用并行工具调用，或添加逻辑确保同一子图不会被多次并行调用。

```typescript
import { createAgent, tool, toolCallLimitMiddleware } from "langchain";
import { MemorySaver, Command, interrupt } from "@langchain/langgraph";
import * as z from "zod";

const fruitInfo = tool(
  (input) => `Info about ${input.fruitName}`,
  {
    name: "fruit_info",
    description: "Look up fruit info.",
    schema: z.object({ fruitName: z.string() }),
  }
);

// Subagent with checkpointer=true for persistent state
const fruitAgent = createAgent({
  model: "gpt-5.4-mini",
  tools: [fruitInfo],
  prompt: "You are a fruit expert. Use the fruit_info tool. Respond in one sentence.",
  checkpointer: true,
});

// Wrap subagent as a tool for the outer agent
const askFruitExpert = tool(
  async (input) => {
    const response = await fruitAgent.invoke({
      messages: [{ role: "user", content: input.question }],
    });
    return response.messages[response.messages.length - 1].content;
  },
  {
    name: "ask_fruit_expert",
    description: "Ask the fruit expert. Use for ALL fruit questions.",
    schema: z.object({ question: z.string() }),
  }
);

// Outer agent with checkpointer
// Use toolCallLimitMiddleware to prevent parallel calls to per-thread subagents,
// which would cause checkpoint conflicts.
const agent = createAgent({
  model: "gpt-5.4-mini",
  tools: [askFruitExpert],
  prompt: "You have a fruit expert. ALWAYS delegate fruit questions to ask_fruit_expert.",
  middleware: [  
    toolCallLimitMiddleware({ toolName: "ask_fruit_expert", runLimit: 1 }),
  ],
  checkpointer: new MemorySaver(),
});
```

当希望像普通函数调用一样运行子代理且无需检查点开销时，可使用此方式。子图无法暂停/恢复，也不具备持久化执行的优势。请使用 `checkpointer=False` 进行编译。

```typescript
const subgraphBuilder = new StateGraph(...);
const subgraph = subgraphBuilder.compile({ checkpointer: false });
```

#### view subgraph state 查看子图状态

启用持久化后我们可以使用子图选项检查子图状态，若采用无状态检查点，则不会保存检查点，因此无法查看子图状态。而且查看子图状态需要langgraph 能够静态发现子图，即子图需要作为节点或者在节点内部被调用，如果子图在工具函数或其他调用中被调用时，此功能无法生效，无论嵌套层级如何，中断信号仍然会被传至顶层。

##### per thread

Returns **accumulated** subgraph state across all invocations on this thread.

返回次线程上所有`subgraph`累计的状态

```typescript
import 'dotenv/config';
import { StateSchema, StateGraph, START, interrupt, MemorySaver, MessagesValue, Command } from '@langchain/langgraph';
import * as z from 'zod';
import { v4 as uuidv4 } from 'uuid';
import { ChatDeepSeek } from '@langchain/deepseek';
import { SystemMessage } from '@langchain/core/messages';

const State = new StateSchema({
    ask: z.string(),
    systemPrompt: z.string().default('你是一个有用的助手，能够帮助人们简洁的回答问题，并且回答的问题不会超过30个子'),
    messages: MessagesValue,
});

const model = new ChatDeepSeek({
    model: 'deepseek-chat',
    apiKey: process.env.DEEPSEEK_API_KEY,
});
```

### 总结

langgraph 是什么？

langgraph 是一款基于langhchain 框架的多智能体，图编排的大模型开发框架。具备以下能力：持久化，中断，人在回路，时间旅行，记忆，容错机制等功能。



#### 持久化

持久化是构建中断，人在回路，时间旅行，记忆，容错机制，错误恢复等的基础，持久化让程序记住了昨天说了什么，更是在多智能体中实现了状态的物理隔离。持久化会保存**每个节点的当前状态的快照**，依据thread_id（会话的唯一标识）和 checkPoint Saver（负责存储状态的对象，有多种实现，比如内存存储MemorySaver 和 数据库存储 SqliteSaver、PostgressSaver）

一个线程通常包括以下的状态，初始状态，用户输入的状态，各个节点执行的状态。



thread_id 是在模型调用时通过`configurable.thread_id`指定，例如

```typescript
agent.invoke({}, {
  configurable: { thread_id: '123', }
})
```

Thread_id 也是存储和搜索检查点的主键，中断后恢复，保存和加载检查点都通过thread_id 实现



检查点是在super-step 中保存的图状态快照，配置了持久化后`compile`里的`checkpointer`配置，这个`checkpointer`有多种实现，比如内存存储MemorySaver 和 数据库存储 SqliteSaver、PostgressSaver）

检查点是stateSnapshot 对象，filed 有`values、next、config、metadata、create_at、parent_config、tasks`

检查点有一个`checkpoint_ns`命名空间，用于标识属于哪个图或者子图。



可以通过`getState`获取图的最新状态，可以通过传入config 获取图最新状态或者某个指定检查点的状态

可以通过`getStateHistory`获取指定线程的完整图的执行历史记录，最新的在第一位，返回的是迭代器，所以我们可以使用`for await`方法去遍历。



如果需要跨线程保存信息，就需要使用Memory store（记忆存储）了，我们需要store 来跨信息保存内容，有许多种实现`InMemoryStore、PostgressStore、MongoDBStore、RedisStore`。其通过一个 tuple 进行命名空间的划分，`memoryStore.put()`进行记忆的存储，`memoryStore.search`进行搜索，搜索结果的包含`key value namespace createAt updateAt`，通过`InMemoryStore`可以配置语义搜索
